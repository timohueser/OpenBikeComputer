# LS021 FLPR display backend

The shipping nRF54LM20 firmware drives the Sharp LS021B7DD02 from the FLPR/VPR00 RISC-V
coprocessor. The live implementation is split across:

- `obc-fw-nrf54l/src/ls021_flpr.rs` — M33 launcher, control block and presenter;
- `obc-fw-nrf54l/src/flpr/flpr_scan.c` — FLPR waveform and row packer;
- `obc-fw-nrf54l/build.rs` — the single-source memory/contract generator;
- `obc-display/src/ls021/` — host-tested geometry, packing and display contracts.

The board README owns the current DK pin map and build/flash procedure. This document records only
the cross-core architecture that must remain synchronized.

## Architecture

The application renders a full 240×320 RGB222 frame into one resident byte-per-pixel plane. A
`RowDiff` computes changed-row spans. The M33 publishes the framebuffer address and at most 16
ascending, disjoint spans, then rings one `CMD_RUN_FRAME`. The FLPR reads and packs those rows
directly while fast-forwarding the gate over unchanged rows.

A full frame is the one-span case `(0, 320)`. Base presents are asynchronous: the FLPR stamps the
completed sequence and triggers EGU20, whose ISR wakes the waiting M33 future. The wait is bounded;
a timeout preserves the last frame and lets higher-level recovery retry or relaunch the coprocessor.

Overlay presents deliberately use a bounded blocking path so their composite/save scratch remains
transient stack storage instead of becoming permanent async-future state.

COM remains an M33-owned high-priority task. It must keep alternating even if display scanning
faults, so it is not part of the FLPR image.

The same coprocessor is time-multiplexed with Nordic's sEMMC soft peripheral. `flpr_mux` owns the
mode. A scan in flight may not be parked; each display request first ensures display mode, and each
storage request waits for the current scan sequence to settle.

## Generated memory map

`build.rs::contract` generates the M33 `memory.x`, FLPR linker script, Rust constants and C header.
Never commit a crate-root `memory.x`: cortex-m-rt would load it before the generated carve and let
the M33 stack overwrite the coprocessor images.

| Region | Range | Size | Owner |
| --- | --- | ---: | --- |
| M33 RAM | `0x2000_0000 .. 0x2007_8000` | 480 KiB | application data, statics and stack |
| sEMMC | `0x2007_8000 .. 0x2007_D000` | 20 KiB | resident storage soft-peripheral image |
| display FLPR | `0x2007_D000 .. 0x2007_E000` | 4 KiB | scan image and leaf stack |
| shared | `0x2007_E000 .. 0x2007_F000` | 4 KiB | cross-core control page |
| reserved top | `0x2007_F000 .. 0x2008_0000` | 4 KiB | VPR context and protected RAM |

The display blob is copied to `FLPR_RAM_BASE`, `INITPC` is set to that address, and `CPURUN` releases
the core. The boot magic and alive/bad-magic stamps catch map or layout drift before a frame runs.

## Control block

The v2 control block is 96 bytes at `0x2007_E000`. Rust's `Control` and C's `flpr_control_t` are
`u32`-only, little-endian layouts with matching static size assertions. Shared constants and the
span count are generated by `build.rs`.

| Offset | Field | Writer | Meaning |
| ---: | --- | --- | --- |
| `0x00` | `magic` | M33 | layout tag `0xF1C0_0002` |
| `0x04` | `m33_seq` | M33 | command sequence and M33→FLPR doorbell |
| `0x08` | `cmd` | M33 | `CMD_RUN_FRAME = 2` |
| `0x0C` | `flpr_seq` | FLPR | serviced sequence |
| `0x10` | `status` | FLPR | dirty-row count or boot status |
| `0x14` | `frame_count` | FLPR | completed frames |
| `0x18` | `fb_addr` | M33 | resident framebuffer base, 240-byte stride |
| `0x1C` | `n_spans` | M33 | number of valid span entries |
| `0x20` | `spans[16]` | M33 | `(start_row << 16) | count` |

There are no ping-pong row descriptors: those predated the resident framebuffer and are retained
only in Git history.

## Ordering and doorbells

M33→FLPR uses the sequence field in shared RAM. The M33 writes payload fields, executes `dsb`, and
writes `m33_seq` last. The FLPR observes the new sequence, fences before reading the payload, writes
status, fences, writes `flpr_seq`, fences again, and triggers EGU20.

The M33 acknowledges only the sequence observed by the EGU20 ISR. Sequence-based in-flight state is
required because a delayed interrupt from frame N must not clear frame N+1 while storage is waiting
to take the coprocessor.

VEVIF works for the sEMMC path after the VPR is running, but the display keeps its verified
shared-sequence/EGU20 channel. That is an implementation choice, not a claim that VEVIF is generally
unavailable.

## Toolchain and build

The blob is freestanding RV32EMC (`-march=rv32emc -mabi=ilp32e`) and needs no libgcc or libc.
`build.rs` accepts `RISCV_GCC`/`RISCV_OBJCOPY` overrides or discovers common bare-metal toolchains.

```sh
brew install riscv64-elf-gcc

cd firmware/obc-fw-nrf54l
cargo build --release --locked
```

The standalone bring-up binaries are retired. Exercise the backend through the shipping image and
the focused host tests for `obc-display`. Current timing evidence and the accepted over-spec source
bus policy live in [`flpr-timing.md`](flpr-timing.md).
