# Web planner

## What it does

This page is the app of the rider at the path `/plan/`. The entry point [`planner.ts`](../../builder/web/src/planner.ts) mounts the shell ([`Shell.svelte`](../../builder/web/src/Shell.svelte)). The shell shows the top bar ([`TopBar.svelte`](../../builder/web/src/components/TopBar.svelte)), one page, and a footer line with the links of the project site, the legal pages and the licence notices that the build writes beside the page.

The hash of the address selects the page, for example `#/planner` or `#/route/ID` ([`routes.ts`](../../builder/web/src/lib/routes.ts)). The table `PAGES` in the shell has one line for each page. A line gives the label of the link in the top bar, if the page has one, and a function that loads the page. A hash with no line in `PAGES` shows the Home page. Each page goes in `src/pages/`. The route planner is the page of route planning (`PlannerApp`). Its line loads the shared WebAssembly core first. When a page cannot load, the shell shows its message.

The planner page stays mounted when another page shows, so its Undo history, its map view and its calculated line stay. The shell hides it and gives it `active` false, and then the planner reads no keys. When the route changes, the shell closes each open modal window, because an open modal window makes the rest of the page inert.

`router.go(hash, state)` puts a new entry in the history with a state for the next page, such as `place` for the planner, `search` for the Routes page or `explore` for the Explore page. `#/planner/new` with `history.state.place = { lon, lat, box? }` opens a new plan and fits the map to the box, or shows the point at zoom 12 when the box has no size. With `history.state.signed`, it plans that route of the catalog in place of an empty plan.

The shell makes the one library of the app (`Library`) and gives it to each page, because a listener of the library hears only the writes of its own object. After the first page shows, the shell starts the cover job.

The settings ([`Settings.svelte`](../../builder/web/src/pages/Settings.svelte)) are a large window over the page, not a page in `PAGES`; the gear at the right end of the top bar opens them. For `#/settings`, the router keeps the route and the id of the page before it, so that page is not created again and keeps its scroll place and its selection. A direct visit shows the window over the first page: the router puts `#/` in the history before it. So each close of the window is Back, and Close, Escape and a click on the dimmed page go back too. The settings set the units, the look, the maximum heart rate and the threshold power, and it saves and loads a backup of the library. "Delete all" empties the library with `clear` and loads the page again, because after `clear` the `Library` object of the tab refuses each write.

The pages reach the browser through one host layer ([`platform/`](../../builder/web/src/lib/platform/index.ts)), the web host. The build configuration ([`vite.config.ts`](../../builder/web/vite.config.ts)) builds this app, TrailView alone and the operator page of `obc data`, each with its own mode. `npm run build:planner` builds the app into `builder/web/dist/planner`. The site deploy copies it to the path `/plan/` of the project site ([`deploy-site.yml`](../../.github/workflows/deploy-site.yml)). The browser tests of the app are in `tests/browser/planner/`.

Route planning owns all the planner code. Web foundations owns the code that the other web systems share too: the window and the controls of `lib/ui`, the page addresses, the theme and the loader of the WebAssembly core. This shell owns the entry point, the shell, the top bar, the pages, their parts in `components/route`, the covers in `lib/covers`, the host layer and the build configuration.

## Home page

The page `#/` ([`Home.svelte`](../../builder/web/src/pages/Home.svelte)) shows the home view of the day ([`View.svelte`](../../builder/web/src/pages/home/View.svelte)), the search, a personal text and a drawer of cards. It reads the library at mount and 200 ms after a write to the routes, the rides or the state; it waits for no map catalogue.

The home views are still images of a set that the owner makes ([home-views.md](../../specs/home-views.md)). `viewAt` takes one view for each local day and its image by the local time ([`views.ts`](../../builder/web/src/pages/home/views.ts)). The image fills a box that the layout sizes, so nothing moves while it loads. A box names the view, offers "Plan a route here" and holds the data credits. An image that fails makes the page read the manifest one more time: a new set shows, and the same set or no answer gives a plain ground in the colours of the theme, with the text in ink and no box. A dev server takes another time from `?now=YYYY-MM-DDTHH:MM`.

The text ([`personal.ts`](../../builder/web/src/pages/home/personal.ts)) is the open plan of the planner (`active`) when it changed in the last 7 days, else the totals of this year when the rider has rides in it, else the slogan. A year with rides by bike and on foot shows the two lengths side by side in one size, each with its word and its count under it, and never adds them; on a narrow screen the second length goes under the first. A year with only one of them shows one large number. An import is dated at the import but is never the open plan, so it shows no "Continue". The search ([`Search.svelte`](../../builder/web/src/pages/home/Search.svelte)) finds the routes and rides by name at each key, and places 300 ms after the last key, around the newest route. A place opens the planner there, or the Routes page with the place as its chip.

The drawer ([`Drawer.svelte`](../../builder/web/src/pages/home/Drawer.svelte)) shows the newest 6 routes or the newest 6 rides, never both: a switch chooses when the library has both kinds. On a first visit it shows the features. A card picture is too small for its credits, so the card gives them to the page: the box of the view lists them, else a fold-out "Data credits" in its place.


## Route page

The page `#/route/ID` ([`Route.svelte`](../../builder/web/src/pages/Route.svelte)) shows one planned route. The numbers come from the stored summary, and the time is the stored time. The page calculates the line again from the plan, with its own cache of legs, for the days, the climbs, the waypoints and the GPX and FIT export ([`Facts.svelte`](../../builder/web/src/components/route/Facts.svelte), `routeFacts`). When the calculated length differs from the stored length by more than 1 %, the card says so until the next save of the route; the planner writes only a missing summary when it opens the plan. With no network, the card shows the routing error, and Export gives only the plan file.

With a cover, the picture shows the whole cover, never cut, and the map ([`RouteMap.svelte`](../../builder/web/src/components/route/RouteMap.svelte)) as a card beside it at the same height. The cover is as high as the frame, but no higher than leaves a third of the width to the map; the place under a lower picture stays free. When the map has less than 260 px beside the cover, the cover is large and cut, and the map is small in a corner; a click on the small one swaps them. With no cover, the map is large and no picture shows. The map shows the relief of the planner map: the hill shading, and the contour lines with their heights. It has no switch for them. The cover record keeps the credits that the still gives. The credits of the map start closed behind the "i" button of the map; a button on the picture shows the credits of the base map and the terrain, and of the cover when there is one. A cover made before the credits were kept shows the credits of the release. The pointer is a share of the summary line from 0 to 1, so the cover and the map mark the same place.

The bottom card ([`Rows.svelte`](../../builder/web/src/components/route/Rows.svelte)) shows the waypoints, the heights, the surface and the places of one category along the route, or along one day of it. The rows share one axis ([`Lanes.svelte`](../../builder/web/src/lib/ui/Lanes.svelte)): the distance from the start of the route. The heights ([`ElevationRow.svelte`](../../builder/web/src/components/route/ElevationRow.svelte)) have the steepness colours of the planner profile (`gradeBands`), and the climbs are those of `routeFacts`. Under the surface bar stands the legend of the planner profile ([`SurfaceLegend.svelte`](../../builder/web/src/components/planner/SurfaceLegend.svelte)): the colour, the name and the share of each surface, the largest first. Unknown stands last and is paler. The shares are those of the stretch that the bar shows, here and in the planner profile, so the legend and the bar agree. They are whole percents that add to 100 (`surfaceShares`). A stretch with no known surface shows "No surface data" in the place of the legend. The pointer or the keyboard focus on an entry lights the stretches of that surface on the bar. An entry has no action, so it is a list item that takes the focus, not a button. With no calculated line, the card shows the heights of the summary and the waypoints at the nearest points of the summary line (`routePins`). Places load only when their row is on the screen, for at most 300 km of the shown stretch. A pointer on the card marks the cover and the map, and the reverse. The large picture, the cover or the map, shows each waypoint as its number in a disc and each night as a moon; a click shows the name. The small picture in the corner shows no pins and no places.

The page has one selected part of the route, as shares of the line. `Lanes` owns how a rider selects it, so that each card on one axis selects a part the same way: a drag, Shift with an arrow key, the line of numbers with Clear in the header, Escape, and the paler rest of the rows. A climb fills its stretch under the profile line. With no selected part, a click on a climb in the elevation row or Enter at a climb selects its stretch as the part. While a part is selected, a click in the rows or Enter only clears it, so a click that clears never selects the climb under it. A click on a climb in the left card always selects it. The left card then opens the climb: the open climb and the part are one state. A chosen day acts as the part while no part is selected. The map and the cover draw the part in the colour of the line and the rest pale; the map fits the part. On the cover the rest has no glow (`REST` of `draw.ts`), so it stays behind the part on a dark slope. With no selected part, a climb under the pointer marks its stretch the same way, but the map does not move. The places of a category are those within its distance from the route, `routeM` in [`poi-kinds.json`](../../builder/web/src/lib/planner/poi-kinds.json). The large map draws each place of the chosen category as a small dot, which is quiet at the zoom of a long day. The pointer on a place or a group in the row, or on a dot, turns the dot of each of its places into the disc of the planner map ([`PlaceDisc.svelte`](../../builder/web/src/components/planner/PlaceDisc.svelte)) and the icon in the row into the same disc. A group opens a list of at most 30 names. A click on a place or on a name opens the details of the place in the popup of the planner map ([`PlacePopup.svelte`](../../builder/web/src/components/route/PlacePopup.svelte)), with where along the route it is and how far from the route, and with no plan actions. When the map is small in the corner, a click on a place makes the map large first, and a click on the small cover closes the popup.

The planner profile uses `Lanes` for its plot, so a rider selects a part there in the same way. The numbers of the part stand in the title row of the drawer and count from the start of the open day, as its ticks do. While a part is selected, the profile keeps the stretch that it shows, also when the map moves. Another line, the switch "Map view / Whole route", another day, another week and a closed drawer end the part. A moved day end and another pace keep it. A trip of 15 riding days or more has the strip of all days ([`TripStrip.svelte`](../../builder/web/src/components/planner/TripStrip.svelte)) in place of the switch: the profile, the day list and the night search show the week that its frame marks ([`week.ts`](../../builder/web/src/lib/planner/week.ts)). The map draws the riding days of the week in their colours and the other days as thin grey lines, with their night marks as small dots and their shaping points hidden; the look of a day is a feature state of the `trip` source, so a week step sends no line to the map, and the map moves to the week only after a move of the strip or of ‹ ›, when the line of the week is not in view. Escape closes the selection of the map or the map mode first, then the part, then a town, a night page or the open day.

A rename calls `renameRoute`, which is the only write that changes the name of a stored route. "Send to device" and "Do not send" change the list `waiting` of the library with `changeState`, and the device sync sends the routes of that list. "Open in planner" goes to `#/planner/ID`: the planner opens that plan and then replaces the address with `#/planner`, so Back returns to the page. `#/planner/new` opens a new plan in the same way.

The Route page and the Routes page show the same state of a route on the device ([`state.ts`](../../builder/web/src/pages/routes/state.ts)): "Waits for the device" for a route in `waiting`; "On the device" for a route in `sent` on the card of the remembered device whose last send finished: the device holds the plan as it is now, except the day routes that the rider deleted there, which a send does not put again; "Changed since it was sent" when its name or its trip differs from the sent ones (`sentKey`). "Send to device" is off only for a route that is on the device. When nothing of a plan is left on the device, the plan is not on it, and a send puts all of it again.

The Route page and the Ride page share their frame ([`Detail.svelte`](../../builder/web/src/components/route/Detail.svelte)): the title row with rename, the left card, the picture ([`Picture.svelte`](../../builder/web/src/components/route/Picture.svelte)) and the Export menu. The button styles of the frame apply only inside it, so they do not reach the planner.

The menu "More" of both pages has "Share" as its first item. It opens the window "Share" ([`Share.svelte`](../../builder/web/src/components/route/Share.svelte)): the share card as the file will be, and beside it the format, the switches of its parts and the buttons. [`card.ts`](../../builder/web/src/lib/covers/card.ts) draws the card into a canvas in three formats: wide (1920 pixels wide), square (1280 × 1280) and tall (1024 × 1280). In each format the whole picture with the line (`drawCover`) stands at the top, 3 : 2 and not cut, and only the product mark stands on it. Under it, on a plain ground, stand the date of a ride, the name, three numbers, one fixed credit line and the elevation profile as a pale shape along the lower edge. `layout` gives the boxes of the parts for a format, with no canvas, and each size is a share of the width of the card. The ground of the wide card is 500 pixels high, and 104 pixels higher for each more line of the name; the ground of a square and of a tall card is the rest of the card. No switch changes the size of a card: the profile takes the height that the text leaves, gets lower when the text needs the room, and goes with its switch when it gets too low.

The picture of the card is the cover, only when its state is `done` and its `lineKey` is the `coverKey` of the record. With no such cover, the window makes the picture of the map at the size of a cover in the light look (`mapPicture` with the size `share`) one time when it opens, and does not store it. A hidden page draws no map, so the window tries again when the page comes into view. Until that picture is there, and when it fails, the top of the card is the line on a plain ground with no credit line. The card changes to the cover when the cover job saves one, and it does not read the credits of a picture. "Hide start and end" leaves out the line in the first and the last 500 m, with the cut inside a segment (`trim` of `drawCover`, `stretch`); a line shorter than 2 km is whole and has no such switch.

After each change the window draws the card and keeps its JPEG file, so a click on a button waits for nothing. "Download" saves that file. "Copy" writes a PNG of the card to the clipboard, and "Share" gives the JPEG file to the share sheet of the system; each of the two shows only where the browser can do it. Safari permits both only in the click itself, so "Share" uses the kept file and "Copy" gives the clipboard the promise of the PNG. A copy or a share that the browser refuses says one sentence in the window. The card has one square box in the window, which holds each format, so a new format moves no other part. The card is the same in both looks, the window remembers no format and no switch, and the card of a ride is the whole ride.

## Ride page

The page `#/ride/KEY` ([`Ride.svelte`](../../builder/web/src/pages/Ride.svelte)) shows one ride. A ride record holds no samples, so the page reads the stored source file one time for each key ([`samples.ts`](../../builder/web/src/lib/ride/samples.ts)): FIT with `readFit`, GPX with `readGpx`, and a device ride with `deviceSamples`. It reads the record again after each write of the ride, for example a rename. Distance, climb and the moving time come from the summary. The speed is the metres of the moving steps over their seconds, as on the device. Heart rate, power and cadence are means over the moving steps of the summary (`movingSteps`), weighed by their seconds ([`numbers.ts`](../../builder/web/src/lib/ride/numbers.ts)); a cadence of 0 does not count. A sensor with no value shows no row and no zones. The zones use the maximum heart rate and the threshold power that the ride brought, else those of the settings; with neither, the card links to Settings. The climbs use the one climb rule (`routeSegments`) in each segment of the ride by itself, so a pause adds no hop to a climb. Their distance has no hop across a pause. A climb shows no grade: recorded heights make it too high.

The bottom card ([`RideLines.svelte`](../../builder/web/src/components/route/RideLines.svelte)) is the sibling of the bottom card of the Route page, in the same frame (`Lanes`). It has one row for each line of the ride that has values: elevation, speed, heart rate, power and cadence; the cadence starts hidden. The axis is the distance with no hop across a pause. A line is the mean over 10 s, then one value for each pixel column ([`lines.ts`](../../builder/web/src/lib/ride/lines.ts)), in one solid colour of its own. The average of a line stands under its name, as the left card gives it; the highest and the lowest value stand after the row, in the same place in every row. A drag selects a part, from one sample to another. The page gives the part to the map and the cover as shares of the summary line (`lineShares`), and the left card shows the numbers and the zones of the part beside the whole ride (`partNumbers`) a moment after the last move of the drag. The scale of a row is the range of its smoothed values, so the top of a row can be lower than the "max" of the left card, which is one sample. The zone bars of the left card and of the Settings use the five zone colours `--zone-1` to `--zone-5`.

The label of a row, its name and average, is a button: it opens that line large in a window ([`RideLarge.svelte`](../../builder/web/src/components/route/RideLarge.svelte)). A click inside a row belongs to the part and the climbs. The window is the `wide` size of the one window of the product (`Window.svelte`) and is local state of the page, with no address. Heart rate and power draw each stretch of the line in the colour of its zone (`zoneStretches`), with a thin rule and the name where a zone starts, and the time in each zone stands beside the line as five bars ([`ZoneTimes.svelte`](../../builder/web/src/components/route/ZoneTimes.svelte), which the left card uses for its bar too). Under the line stand the average and the highest value. Speed and cadence keep their colour and have no zones. The elevation has the grade colours of the Route page, with the lowest and the highest height. With no limit for a sensor, the line keeps its colour and the window shows the link to the Settings. The window has its own pointer, which does not move the map. On a phone the zone times stand under the line.

The window shows a stretch of the line, its view, always on the distance axis. A drag across the line makes that stretch the view, a pinch on a trackpad changes the length of the view about the pointer, and a sideways scroll moves it. A view is at least 200 m long (`fitView`). The ticks, the scale, the numbers and the zone times are of the view (`partNumbers`), and the range of the view stands beside the numbers. The scale of a view is at least a quarter of the scale of the whole line, so a flat stretch stays flat. The zone times of a short view are in minutes and seconds. While the window shows less than the whole ride, the button "Whole ride" stands beside the title, where the eye is at the end of a drag: the title row holds the two ways back, out of the view and out of the window. Escape takes them in that order, and a double click on the line shows the whole ride too. The window opens on a selected part, and while the view is that of the part, the numbers are of the samples of the part, as in the left card. In a longer view the part shows as in the rows, with no edge where it runs past the view, and a click on it makes it the view. No drag in the window changes the part.

The name of the axis beside the ticks, "Distance" or "Time", is the switch of the axis; on a phone it stands under the ticks. The choice lasts as long as the page shows the ride. The time axis is the time of day (`timeAxis`): a stop has a width there, and no line leads across a step of more than a minute. The foot of the pointer says the time at the place of the pointer; in such a step the rows show no value. A stop is a run of steps that do not move, with a segment start in it or 5 min or more long (`stops`). It is a mark on the row of the ticks only: a short dash on the distance axis, a bar as long as the stop on the time axis. It has no text; with the pointer on it, the foot of the pointer adds its length. On the distance axis a stop is one place, so a part does not begin or end in it (`outOfStops`). A click on a climb in the left card selects it as the part, as a click on it in the elevation row does; the rule of the Route page for a click while a part is selected applies here too. The window of one line stays on the distance axis. With every line hidden, the card shows its chips only.

With a part selected, the menu "More" has the switch "Only the selected part" over its exports. With it on, the FIT file, the GPX track and the table come from the samples of the part (`slice`, whose first sample starts a segment), and the name of the file ends with "part".

The frame of a detail page ([`Detail.svelte`](../../builder/web/src/components/route/Detail.svelte)) does not scroll as a whole on a computer: the cards take the height that the bottom card leaves, down to 160 px, the rows of the lines get lower in a low window, and the left card scrolls inside. No bottom card is a scroll box, so its panels are never cut. A menu is the one of [web-foundations](web-foundations.md) ([`Menu.svelte`](../../builder/web/src/lib/ui/Menu.svelte)).

The line of a ride is a teal: a lighter teal with a glow on the cover, and `--ride` on the map and on the plain ground. Export gives the stored file for its own format, else a file written from the samples, and a CSV table in SI units. "Ride it again" opens the route of the ride's line. Its id is the id that "Add files" gives the same line (`lineId`), so a second click opens the same route. After Delete, the page goes to `#/routes/ridden`.

A ride can have photos. "Add photos", the second item of the menu "More", and a drop of files on the page open the window "Add photos" ([`AddPhotos.svelte`](../../builder/web/src/components/route/AddPhotos.svelte)). The window reads the time, the zone and the GPS place of each file (`photoFacts` of the library) and finds the place of the photo on the ride ([`photos.ts`](../../builder/web/src/lib/ride/photos.ts)): the clock time with the zone of the file, else the GPS time, else the clock time in the zone of the browser; a clock time with no zone, and a GPS place within 100 m of the line, takes the whole hours from the zone of the browser that put the photo nearest to that place. A photo with no time, and each photo of a ride with no times, is of the ride when its GPS place is within 100 m of the line, at the first pass. A photo with a time outside the ride is not of the ride. The window shows the photos of the ride as small pictures, says how many files are not of the ride, how many are HEIC files that the browser cannot open, and how many other files it cannot open, and then adds one photo at a time (`addPhoto` of the library). The library reads the time of a HEIC file from its EXIF item, so Safari, which opens HEIC files, adds them. The page reads the photos of the ride again after each write of a photo, and finds the sample of each one. A photo is a small picture with a white edge on the cover and on the map ([`PhotoMarks.svelte`](../../builder/web/src/components/route/PhotoMarks.svelte)), where the pins are: photos closer than 40 px are one mark with a count, and a place of the line that the cover hides has no mark there. On the row of the ticks a photo is a dot; dots that touch are one dot, and on the time axis a photo with a time stands at its time. A click on a mark or a dot opens the photo window ([`Photos.svelte`](../../builder/web/src/components/route/Photos.svelte)): one photo large in a frame of one size, the list of all photos of the ride beside it, the place and the time of day under it, "Use for the card", and "Remove", which asks no question. "Use for the card" writes the id of the photo into the ride record (`setCardPhoto`), and a second click removes it; "Remove" of that photo removes it too. A card and a row of the ride ([`Cover.svelte`](../../builder/web/src/lib/covers/Cover.svelte) with the place `card` or `row`) then show the copy of that photo in place of the cover; the page of the ride keeps the cover. The product never chooses a photo. The window reads the copy of a photo only when that photo shows; the marks and the list use the small pictures.

## Routes page

The page `#/routes` ([`Routes.svelte`](../../builder/web/src/pages/Routes.svelte)) lists the planned routes, and `#/routes/ridden` lists the rides. Each view has its own entry of the history and its own search. The page shows them on a map ([`RoutesMap.svelte`](../../builder/web/src/pages/routes/RoutesMap.svelte)), and shows the selected row in a card over the map ([`SelectedCard.svelte`](../../builder/web/src/pages/routes/SelectedCard.svelte)). Three parts draw the page and know nothing of the library: the frame with the header, the list and the map ([`ListAndMap.svelte`](../../builder/web/src/pages/routes/ListAndMap.svelte)), a row of the list ([`RouteRow.svelte`](../../builder/web/src/pages/routes/RouteRow.svelte)) and the card ([`RouteCard.svelte`](../../builder/web/src/pages/routes/RouteCard.svelte)). The page and `SelectedCard` give them text, numbers and snippets, and keep the reads and writes of the library. The list is a third of the window wide, from 380 px to 480 px; on a phone the page is one column. The list shows from the library alone. The map, the place search and the titles of plans with no name load the map catalogue, so they come after the list.

The list, the map and the card read plain items: kind, id, name, summary and a time, the last change of a route or the start of a ride ([`filter.ts`](../../builder/web/src/pages/routes/filter.ts)). The rides have the chips place, year, kind of bike and length. A route that is not a plan has no summary: it shows no line and no send button. The search is one object of chips (`Chips`): kind of bike, place, length, climb and days. The rider sets them from a menu ([`Chips.svelte`](../../builder/web/src/pages/routes/Chips.svelte)), or presses Enter in the field: `readSearch` turns a place that the text names into a chip and keeps the rest of the text. A later search that understands requests can fill the same chips. A place matches a line that comes within 2 to 10 km of the bounds of the place, by its kind; the nearest line comes first, else the last changed. "Only in this map view" keeps the routes with a point in the view, and the map then does not move by itself.

The map shows the relief of the planner map: the hill shading and the contour lines. It has no switch for them. It draws the lines from zoom 8. Below zoom 8, bubbles count the shown routes, and a click on a bubble zooms in. The map of the Explore page has no bubbles and draws its lines at each zoom: Explore lists single routes only in views where their lines can be read, so a bubble would count a list that is already out of date. The selected route draws wide at each zoom. The picture of a row is 150 × 100 px, and 120 × 80 px on a phone. A row of the list shows its picture only while it is near the view. A row near the view asks for the cover; the card asks for the cover and the map picture. A row shows the map picture only when the record already has one, because each map picture downloads map tiles. The credits start closed behind the "i" button of the map. The button opens the credits of the base map, the terrain and the picture of the card together; the card is too small for its own credits. The link of the name of the route covers the card under the buttons; a pointer over the card underlines the name. The card of a route that the planner can read (`plan` of the item) has the filled link "Open in planner" to `#/planner/ID` over the quiet button "Send to device". The link shows after the planner code has loaded, and a plan with no line has it too. A click on the map where no route is, Escape, or the close button of the card closes the card and clears the selection. The close button first moves the focus to the row of the item, because the button goes with the card. The card is at most 980 px wide and stands in the middle of the bottom of the map. It has three layouts by its own width, not by the width of the window: wider than 740 px the picture is 300 × 200 px and the profile is a strip beside it under the text and the buttons; up to 740 px the picture is 35 % of the card and the strip is under the whole card; up to 480 px the picture is 120 × 80 px and the buttons are a row under it. So it looks the same in each place that shows it. The card over the map is never higher than the map less 24 px: a lower picture and a scrolling text keep the whole card with its close button in the map. In a window at most 480 px high, a card up to 740 px wide with a text under its buttons shows no profile strip, so that the text keeps its room. On a phone the map is under the list, so the card is fixed at the bottom of the screen: a tap on a row shows it. The document then has the height of the card as room at its end, so the card covers nothing there. The fixed card is never higher than the screen less 96 px: a text that is too long scrolls inside the card, and the close button and the buttons of the card stay on the screen. The credits of the map end before the buttons that a page puts beside the zoom buttons.

A row and the lines of its row light together ([`hover.svelte.ts`](../../builder/web/src/pages/routes/hover.svelte.ts)): the pointer on a row lights its lines on the map, and the pointer on a line lights its row. The list never scrolls to it, and the map never moves to it. A tap lights nothing, and the map lights a line under the pointer only on a device whose pointer hovers.

They show only lines that the map shows, in the zoom range of the lines, so a Routes map below zoom 8 lights nothing. A selected route shows its mark on touch too.

## Explore page

The page `#/explore` ([`Explore.svelte`](../../builder/web/src/pages/Explore.svelte)) lists the signed hikes of the map view: the route records of the route catalog ([route-catalog.md](../../specs/route-catalog.md)) of the kind hiking. The bike kinds show in the search bar, greyed out: the search is built for hikes only. It uses the frame, the row, the card and the map of the Routes page, and reads nothing of the library. A catalog record is a third kind of item (`signedItem` of [`filter.ts`](../../builder/web/src/pages/routes/filter.ts)): the height of each point of its line is the profile of the record at the share of the line's length that the point has.

The day routes tab is a search: the search bar over the page, the map, and the results in a table under the map, with a handle that sets the height of the table (`PanelResize`). [`search.ts`](../../builder/web/src/pages/explore/search.ts) answers the query in the browser: the reach, the rows of each shape, the limits, the wishes, the order, the counts and the changes that help an empty list. A release with no facts files ([route-catalog.md](../../specs/route-catalog.md#facts-files)) searches the route records alone. The page loads the cell files and the facts files of the map view, or with a start point of the part of the view in reach (`loadBox`), and shows a row only when the facts files of its cells have loaded (`catalog.factsInBox`). The far files of those cells decide which records are day routes. With a start point, a change of tab loads files, because the long trails tab reads the whole view.

The search bar ([`SearchBar.svelte`](../../builder/web/src/lib/ui/search-bar/SearchBar.svelte)) has the field "Find a place" before it and three fixed slots: "From", "Hike" and "On the way". Each slot shows its values as words in a fixed order, the first two and a count of the others, or its default in a quiet style ([`slots.ts`](../../builder/web/src/pages/explore/slots.ts)). A click opens the panel of the slot under it; one panel is open at a time. "Done", Escape and a press outside the bar close it, and that press still acts where it lands, so a click on the map picks a start point or a place. Each slot owns its fields of the query (`SLOT_FIELDS`), and its "Reset" gives them their defaults. The cross empties the search, and for 8 s "Undo" brings it back. "From" and "On the way" are off on the long trails tab and in a release with no facts files: the page then searches with their defaults (`effectiveQuery`) and keeps the query itself, so its values come back where the slot is on again.

"From" is Getting there ([`Journey.svelte`](../../builder/web/src/pages/explore/Journey.svelte)): a line from the start point through Car, Train (later) and Lifts to one walk to the route. With no start point every hike of the map view counts, and only Lifts shows, because it adds the lift shapes. "Pick on the map" closes the panel and takes the start point from the next click on the map, and "My location" from the browser; when the browser gives none, a short note says so. A new way of getting there fits the map to the box of the reach, or to the walk around a pinned start. "Hike" has five rows ([`HikePanel.svelte`](../../builder/web/src/pages/explore/HikePanel.svelte)): each row shows its value, and a click shows its control. The kind has hiking only. The shape has all four tiles; a lift tile shows as pressed only while lifts are on, and a click on it turns lifts on. Length and Climb use the slider of the Routes page with a fixed scale of 30 km and 1,500 m, so the scale does not jump when the loaded hikes change. Path difficulty ([`GradeRange.svelte`](../../builder/web/src/pages/explore/GradeRange.svelte)) is one range of T grades: each grade shows a drawing and its description after a second under the pointer, at once on a key focus, and until the next click after a click. While a grade limit is set, "Include routes with an unknown grade", on by default, keeps the routes with no grade and shows their count. On the long trails tab only the kind and the hardest grade apply. In "On the way" ([`Wishes.svelte`](../../builder/web/src/pages/explore/Wishes.svelte)) a tick makes a wish a must, and "Must" off makes it a nice wish that only sorts. A wish shows the count of rows that meet it. A wish with no data for the loaded hikes shows "no data", and a wish that leaves no hike is not offered. "Official route" shows only while a made route is loaded. "Free of snow" holds the day of the hike: a new day ticks it, and an untick sets the day back to today.

The line over the table ([`ResultsTable.svelte`](../../builder/web/src/pages/explore/ResultsTable.svelte)) has the count. A row is one route in one shape. The Shape column shows a picture and a word, and below 1,180 px the picture alone; Getting there shows the steps of the cheapest way, and with no start point the car park or the lift at the route; Best fit shows each nice wish, filled when the row meets it. A click on a column header sorts by that column; Best fit is the order of the search. A click on a row opens it in place: the cover, the name with a link to the page of the route, the numbers with the descent of a lift shape, the shape and the way there in words, the wishes it meets and misses, the profile, the highest point, the snow window, the paved and forest shares, the places it passes, and "Plan this route". An empty list names the first four changes that give rows, each with its count, and a click applies one. A row and its line light together, `show` opens the row of its route, and TrailView shows the routes of the rows.

The map of the search ([`search-map.ts`](../../builder/web/src/pages/explore/search-map.ts)) marks only what the search needs. A car park or a lift shows when the cheapest way of a row uses it, or with no start point when the row names it in Getting there; such a marker shows from zoom 11, because a wide view holds one for most rows. A summit, hut, lake or waterfall of the facts files shows when its kind is a wish and a row passes it, when it is a "Passes" wish, and when it is on the route under the pointer, else on the open row. Those two show the names. Places that overlap hide each other, the one on the lit row first; a car park or a lift that a row uses always shows. A lift has a dotted cable to its valley station. The start point has a ring of its first leg: the drive with the car, else the walk; it takes no click. A click on a car park or a top station pins it as the only start, and a second click unpins it. A click on a place sets the must wish "Passes <name>", and a second click removes it. Under the pointer, a marker names what a click does and how many hikes it keeps. An open row moves the map only when its route is not all in view: the map pans or zooms out, never in, so the list keeps its rows. A late answer of "My location" does not replace a start or a pin that the rider set meanwhile.

While the search shows, the page address holds the query and the view as parameters after `?` (`#/explore?car=1&must=hut&view=…`, `queryParams`); the router reads only the part before `?`. The page reads the query from its address, else from `history.state.explore.query`, else from the last query of the browser (`localStorage`). So after a reload, "‹ Explore" of a route page opens the last search of the browser with the view and `show` of the route. When that search leaves the route out, also by a start point elsewhere, the page opens the default search in the view of the route, so the row of the route opens. The history keeps the query, the selected route and the shape of its open row.

The map gives the page its first view, and then each view in which it is still for 100 ms, so a zoom in steps changes the list once, at its end. The Routes page gets its views in the same way. A view whose catalog files are loaded then shows its routes at once (`catalog.inBoxNow` of [`route-catalog.ts`](../../builder/web/src/lib/planner/route-catalog.ts)). For another view, the page loads the files 200 ms later (`catalog.inBox`), and keeps only the answer of its last load. Until that answer comes, the list shows the routes of the last answer that are in the new view, else grey rows. The list has no groups: the shortest route comes first, then the lowest relation id. The map does not move after a read. The field "Find a place" finds places only, and a place moves the map. A row and the card show the cover of the route in the live set of route pictures, else its line on a plain ground. The list draws its first 60 rows, and 60 more each time the rider scrolls near their end. A new answer, a new grade or a new tab start the list at its top with its first 60 rows again ([`rows.ts`](../../builder/web/src/pages/explore/rows.ts)). The selected route always has its row, and the list scrolls to it: after a selection on the map or in TrailView, and in a new list.

With trail files, the page has two tabs beside its title, in the control of the Routes page: "Day routes N" and "Long trails N". The page opens on the day routes, and only the rider changes the tab. A record is no day route when its long trail is a trail of the far files of the view ([route-catalog.md](../../specs/route-catalog.md#trail-files)): for a stage or a section, the trail of its long route, or else the complete long route of a stage (`parent`), which can hold a long route that is no trail; for any other record, the record itself (`longTrailId` of [`signed-routes.ts`](../../builder/web/src/lib/planner/signed-routes.ts), `farTrailId`, `splitDay`). Nothing else decides, so no stage of a trail is a day route. The long trails tab lists each trail whose far line meets the view, and the trail of each record that the day routes lose, so a stage at the edge of the view keeps its trail row (`nearTrails`). The records and the far files of a view load together (`catalog.trailsOfCellsNow` gives every trail of the far files of the view), so the day routes never show a list that is not split yet, and with no start point a tab change loads nothing. A failed file fails both tabs. N is the count of rows that the tab lists with the search; a tab with no list for the view shows its name only. The rows of a tab need no count line. The map draws only the lines of the open tab. A release with no trail files has no tabs: the list holds every route record of the view, with a count line.

A view that needs more than 12 catalog files is a far view: the day routes tab asks the rider to zoom in, and the long trails tab lists the trails of the far files (`catalog.trailsInBox`). A view that needs more than 12 far files asks the rider to zoom in in both tabs. A trail is a fourth kind of item (`trailItem`): its line is its far line, and it has no cover. In a far view the map draws each trail with a gap where its far line breaks. In a near view it draws the stage lines of the cell files in the colour of their trail: a far line is up to 110 m from its route and cuts the bends of a mountain path. The trails sort by network level, international first, then the longest first, then the lowest relation id. The long trails keep the hardest grade of the search; its length and climb are for day routes, because a trail of 400 km matches no range of day routes. TrailView shows the day routes of a near view only, so its control shows only there.

A click on a trail opens the trail card ([`TrailCard.svelte`](../../builder/web/src/pages/explore/TrailCard.svelte)): the far line, the mark, the shape, the network level and the numbers at once, and the number of stages ("7 of 20 stages" when the catalog holds only some, "20 stages, none listed" when it holds none), the profile of the whole trail, the strip of its parts and the credit of a second source when its trail record file loads (`catalog.trail`). The map credits then list that credit too. The name of the card links to the page of the trail ("Trail page"). Each cell of the strip ([`strip.ts`](../../builder/web/src/pages/explore/strip.ts)) is as wide as its part. A part that the catalog does not hold is a grey dashed cell, and a part after a jump has a gap before it. The stage numbers show only when each cell has room for its number. With no numbers and cells under 12 px on average, the strip is one bar with filled and empty runs. A trail that is one route record has the card of a route. Each tab keeps its own selection and card: the day routes tab a route, the long trails tab a trail and one of its stages. The trail stays selected when the rider zooms in, and the map then marks each of its parts in the view; with a stage card open, it marks only that stage. A click on a stage line opens the card of its trail, or the card of the stage when its trail is the selected one; a stage of a trail inside another trail opens the inner trail. The map does not move to a selected trail, because a trail runs out of most views. In a near view, a trail row lights the stage lines of its trail, and a stage line lights its trail row. The history keeps the tab and the selection of each tab. The close button, Escape or a click on the map where no line is clears the selection of the open tab. In the card of a stage or a section in the long trails tab, the name of its trail is a button that opens the trail card, when the long route has two or more stages or is a stage itself; the focus then moves to the trail card. A view whose far files are loaded gets its trails at once, as a near view gets its routes.

Each signed route has one colour of a set of 7 ([`route-colors.ts`](../../builder/web/src/lib/planner/route-colors.ts)): a hash of its OSM relation ID picks it, so a route keeps its colour in each view and after a rebake. Its line, its row picture and its card picture use that colour. A stage or a route in the long trails tab takes the colour of its trail. While a route is selected, the other signed lines dim. A signed line is 2 px wide up to zoom 9, where a view shows many routes, and 4 px from zoom 15. The set is too dark for the dark map, so in the dark theme each signed line has a light edge. The plain pictures have one light ground in both themes. The routes and rides of the rider keep `--route` and `--ride`.

The card ([`SignedCard.svelte`](../../builder/web/src/pages/explore/SignedCard.svelte)) shows the line, the route mark, the shape, the stage with its long route, the network level, the length, the climb, the hardest grade, the profile, the description, the operator and the official page. It shows no time; the page of the route shows the stored time of the catalog (`moving_s`). The name of the card links to the page of the route ("Signed route page"), except in the TrailView window, where Back from the page would start TrailView again. The card and the page show the OSM description of a record only when it says something that the record does not (`shownDescription` of [`signed-page.ts`](../../builder/web/src/pages/explore/signed-page.ts)): at least 3 new words, and no list of places. A word is new when the name, the ref and the operator of the record and of its long route do not hold it, and it is no word for a stage, such as "Etappe". A list of places has a dash, an arrow or » between two words and no new word of more than 3 letters with a small first letter. The text stays as OSM has it, in the language of the mapper. "Plan this route" opens `#/planner/new` with `history.state.signed`: the record, its plan, and the view, the search, the tab and the selection of each tab. The planner makes the plan with `planSignedRoute`, and its "Find another route" opens Explore with that state again. The page also keeps that state in `history.state.explore`, so Back brings it again. A route from a second source ([route-catalog.md](../../specs/route-catalog.md), `credit`) shows the credit of that source on its card. The credits of the map and of the TrailView window list each credit of the routes that they show once. Only the page of a signed route and the page of a trail give it a view: the box of the line, with the hike to show (`show`) or the trail.

When the page opens with `show` in `history.state.explore`, the first answer decides where the record shows (`showAt` of [`filter.ts`](../../builder/web/src/pages/routes/filter.ts)), with the rule that splits the tabs: a day route opens its card on the day routes tab, a stage or a section of a far trail opens its trail and its stage card on the long trails tab, and a far trail opens its trail card. A record that the answer does not hold selects nothing. `show` names a route record only: the page of a trail gives the long trails tab and the trail.

When the browser has WebGPU and the release has TrailView, the control "TrailView" beside the zoom buttons of the map, in their look, opens the TrailView window of the planner ([`TrailViewWindow.svelte`](../../builder/web/src/components/planner/TrailViewWindow.svelte)) with the first 100 routes of the list. With more routes in the list, the tooltip of the control says so. A selected route that is not among them takes the place of the 100th. When the map view or the search change while the window loads, it does not open. The camera is the cover view of their lines (`coverView`) at the size of the window. With no cover view, the page says so and opens nothing. Each route keeps its colour. The route under the pointer is bold; with none, the selected route is bold. A click on a route selects it, and the window shows the card of the page's selection. A click where no route is clears the selection, as on the map. The close button of the card in the window moves the focus to the view. The page and the window share that selection, so the page shows the same card after the window closes.

## Signed route page

The page `#/signed/<cell>/<id>` ([`Signed.svelte`](../../builder/web/src/pages/Signed.svelte)) shows one route record of the catalog: a day route, a stage or a section of a long trail, or a route of a second source. `<cell>` is the first cell of `cells` that the release covers (`signedHref`), so the page loads that one cell file through the catalog of Explore; from a card it requests no catalog file. A record that the cell file does not hold, a cell outside the release and a zoom other than 9 show "This route is no longer in the map data." and a link to the area of the cell on Explore.

The page uses the frame, the left card, the picture and the bottom card of the Route page, and reads no library. It shows the length, the climb and the hardest grade of the card, from the record. The time is the stored time of the record (`moving_s`, the time of its plan at the pace of a new plan), from the first frame, so a stage has the time of its row on the trail page; a record with no stored time shows the time of the routing answer. The line, the heights and the highest point come from the routing answer, so the map and the bottom card measure along one line. It makes the plan of the record as "Plan this route" makes it (`planTrip(routeBase(…), routePlan(record), loop)`), at the pace of a new plan, and calculates its line with one route request. Before the answer, it shows the line of the record and "–" for the highest point, and the surface lane waits empty; the answer brings the highest point, the list of climbs, the surface, the places and Export (GPX and FIT), and changes neither the length, the climb nor a stored time. A routing error removes the surface lane. The title row has the route mark, the name, the place of a stage in its long route (`stagePart`, the rule of the card: a stage whose own long route has fewer than two stages is named in its `parent`), "Plan this route", "Official page ↗" when the record has a website, and Export. The left card has the kind line, the numbers, the strip of the parts of its trail with this part marked and links to the parts before and after it, the description, the climbs, and at its end the operator and the credits. The picture is the cover of the live set of route pictures with the map beside it, else the map alone. The page waits at most 300 ms for the cover before it lays out the picture: from a card the cover comes from the browser cache within this time, so the cover and the map show together. The line has the colour of the route, or of its trail for a part. The name of its trail is the name of the trail record, which the cell file of a part holds. It links to the page of the trail ("Trail page") when the trail record file has loaded; until then it is plain text.

The top bar marks Explore while the page shows. "‹ Explore" is Back when the page before it in this tab was Explore (`router.from`). Else, also after a reload, it opens Explore with `history.state.explore = { view, show }`: the box of its line, and the id of a hike. "Plan this route" gives the planner the same state for "Find another route".

## Trail page

The page `#/trail/<id>` ([`Trail.svelte`](../../builder/web/src/pages/Trail.svelte)) shows one long trail: a trail record with stages and no line of its own. It uses the frame of the Route page, a left card of its own ([`TrailFacts.svelte`](../../builder/web/src/pages/explore/TrailFacts.svelte)), the map of Explore and the profile row of the Route page. The title row has the trail mark, the name, the count of stages of the trail card (`stageCount`: "5 stages", "16 of 108 stages") and "Official page ↗" when the record has a website. It has no main button. The left card has the kind line, the length, the climb, the time when the record has `moving_s`, the count of stages, the description by the rule of the card, a row for each stage, and at its end the operator and the credits. A row has the name of its part (`partLabel` of [`signed-page.ts`](../../builder/web/src/pages/explore/signed-page.ts), such as "Stage 3 · Section 1" for a section of a cut stage), and the length, the climb, the time and the grade that the part has. It opens the page of the stage. A part inside the area of the release that the catalog does not hold (a gap) has a pale row with no link that says "Not in the map data". A part outside the area of the release has no row: the count in the title tells how many stages the catalog holds. The map draws the line of each stage in the catalog in the colour of the trail, with a white dot with a ring where each stage but the first starts. The bottom card shows the heights of the whole trail (`trail_profile_m`) on the axis of `end_m`, a dashed line at each stage end, and the stage numbers in the row of the distances when each stage is at least 18 px wide. At a gap the line on the map and the profile break. The pointer on a row, a line or a stretch of the profile lights that stage in all three places; the lit line has no start mark, because the dots mark where the stages start. A click on a line opens the page of its stage.

The page reads the trail record file (`catalog.trail`) for all but the map, and makes no route request. The map waits for the cell files of the stages whose records the catalog does not hold: a stage takes a cell that an earlier stage took, else its first covered cell (`stageCells` of [`trail-page.ts`](../../builder/web/src/pages/explore/trail-page.ts)). Until they answer, the picture is the waiting surface of the Signed route page. Then the map shows once, framed on the box of the stage lines with 48 px to each edge, clear of the map buttons, and it does not move by itself. From Explore the cells are loaded, so the map shows at once. A trail that is one route record replaces the address with its route page. An id with no trail record file shows "This trail is no longer in the map data." and a link to the long trails tab of Explore.

The top bar marks Explore while the page shows. The name of the trail card and the trail name on a stage page link to the page. "‹ Explore" is Back when the page before it in this tab was Explore. Else it opens Explore with `history.state.explore = { view, tab, trail }`: the box of the stage lines, the long trails tab and, for a hiking trail, the trail, whose card Explore opens as from its history.

## Device sync

The shell syncs routes and rides with one device on the cable: the remembered device ([`remembered.svelte.ts`](../../builder/web/src/lib/device-sync/remembered.svelte.ts)). Only the Connect button of the Device page remembers a device (`rememberDevice`). `localStorage` keeps it in the key `obc-device`. With no remembered device, the shell opens no device session, and no sync runs.

A sync ([`state.svelte.ts`](../../builder/web/src/lib/device-sync/state.svelte.ts)) starts on each `ready` of the remembered device, after `rememberDevice`, on `deviceSync.run()`, and when a route starts to wait or to leave. It holds the Web Lock `obc-device-sync`, so one tab syncs at a time. The sync ([`sync.ts`](../../builder/web/src/lib/device-sync/sync.ts)) does these steps in this order:

1. It lists the card. `sent` names for each route on a device its card (`card`, the store id) and its objects, so a route sent to another card is not on this card: the sync removes nothing for it, and a new send creates it. An object that the listing does not hold is gone.
2. It takes each finished ride that the library does not hold and did not delete, the oldest first, and stores it with its file. The ride brings the maximum heart rate and the threshold power of the device to the settings. A demo ride, a ride with no points and a ride with no clock stay on the device, and `skipped` remembers them.
3. When the browser keeps the library on a full disk (`persist`), the sync marks the stored rides on the device as taken (`ARCHIVE_RIDE`). It marks a ride only when the stored file has the length and the CRC of the object on the card.
4. It removes each route of `leaving` from the device: the trip object, then the day routes. A device refusal of one ride, one mark or one route goes into `problem`, and the sync goes on.
5. It sends each route of `waiting` ([`route.ts`](../../builder/web/src/lib/device-sync/route.ts), [`trip.ts`](../../builder/web/src/lib/device-sync/trip.ts)). It calculates the line again with the routing service, because the summary line is too coarse for the device. With no network, the route waits. A route whose line has a leg with no legal path waits too, and `problem` gives the number of such legs; a point that the line passes by does not stop the send.
   - A plan of one riding day goes as one OBCR route, with its stops as waypoints, 32 at most.
   - A plan of several riding days goes as the phone sends a trip: one OBCR route for each riding day, then one trip object ([`ble-interface.md`](../../specs/ble-interface.md) §7.7) that lists them. The device reads 32 days of a trip object, so a plan of 33 to 64 riding days goes in two parts: days 1 to 32 are the trip object "‹name› 1/2", days 33 to 64 the trip object "‹name› 2/2", each with its own trip key and the start date of its first riding day. The day ends are those of the stored plan: kept nights, moved day ends, else the even day ends. A suggested night town is not used. A day after a train or bus starts where it arrives. A day route is named "Day 3 ‹place of its kept night›", or "Day 3" with no kept night and for the last day, with the number of the day in its part, as the device shows it; its waypoints are its stops. The trip key comes from the plan id, the ids of the first two route points and the part, so the device keeps the progress of the trip while they stay. The trip object has no rest days, so on the device the dates after a rest day are one day early until the rider rides.
   - First the sync takes the copy that a lost put answer left on the card and that no entry names: a day route with the same length, CRC and name. Before the put of a trip object, the entry stores its trip key (`tripKeys`); a part with no trip object takes the trip object with that key or the key of the part now, also in step 4 and for a plan that became one day. The key comes from the plan id, so a trip of the phone (random key) or of another plan never has it.
   - A trip object is the planner's when an entry on the card names it, or when its trip key is one that an entry stores, on any card, or that the plan gives now. Else it is foreign, such as a trip of the phone, which takes routes into its trips by their content. On a card where the entry has no trip object for a part, the sync takes the trip object with the key of the part, so a send to another bike computer in between leaves no second trip. A route that a foreign trip object lists is not the planner's to change: the entry forgets it, and the sync never takes, replaces or removes it. It makes a new route for that day.
   - A day route that is gone from the card, and whose new file has the CRC that `sent` keeps for it, is left out: the rider deleted it on the device, it needs no room, and its trip object lists its old id, which the device skips. The card never gives an object id again, so an old id never names another object. A changed day goes again with a new id, so only what changed takes room. An entry of which nothing is on the card counts as no entry, so a send puts all of the plan again.
   - First the sync removes the trip objects of the parts that the plan no longer has; a plan of one day also removes its other days. Then it sends part 1, then part 2. A part whose days are all left out and whose trip object is not on the card is skipped. For each other part it checks the room of the device menu: 64 routes and 16 trips, with the routes that part 1 made. When the new objects of a part do not fit, the plan stops and waits, a part that went stays on the device, and `problem` says how many routes it needs ("Part 2 of “Alps” waits: …"). Then an object whose copy on the card has the same length and CRC is skipped, an object of the entry is replaced in place, and a missing one is created, and then the trip object of the part. After all parts the sync removes the days that the plan no longer has, so a refused removal leaves no removed day in a trip object. When the new days of a part do not fit before that removal, those days go first, because the device menu shows only the newest 64 routes; until the new trip object goes, the old one names removed days, which the device skips.
   - `sent` keeps the id and the CRC of the file of each object right after its put or removal, and, when the send finished, the `sentKey` of the route: a hash of its name and its plan. A route whose key differs changed since it was sent. A route that the rider deleted during its upload goes into `leaving`.
6. For each day route of `sent` that is no longer on the card, it writes the id into `gone`: the rider deleted the route on the device, for example to make room, and the route stays on the device; nothing goes again by itself. A gone trip object empties its slot, and while a day of its part is on the card also the `key` of the route, so the next send makes it again. The entry keeps the objects that are left, so a delete removes them and a new send replaces them in place. An entry with no object left goes: a delete of a trip on the device removes the trip and its routes. It remembers the map, the number of routes and the bytes on the card, and the rides that came in today.

A pulled cable stops the sync. The library stores a ride only after its whole download, and each object of a route goes into `sent` right after its put, so the next connection sends only the rest. After "Delete all", the next connection takes each ride again, and the sent routes stay on the device. A `sent` value that fails its check reads as empty: the routes that it named stay on the device as single routes.

### The map send

A sync never builds a map. Only `deviceSync.sendMap()` does, and only the button "Send the map" of the Device page calls it. The sync and the map send use the one link to the device, so each waits for the other: a sync does not start while a map send runs, and a map send that the rider asks for during a sync starts after it. A map send ends with a sync, which reads the card again.

`sendMap` ([`sync.ts`](../../builder/web/src/lib/device-sync/sync.ts)) reads the library state `nextMap` and calls the build. The build of the app is `buildMap` ([`map.svelte.ts`](../../builder/web/src/lib/device-sync/map.svelte.ts)). It makes the selection of map assembly from `nextMap`, waits until the run is ready (the catalog indices, the cell lists of the regions and the memory check of the assembly worker), and then downloads the cells, assembles the map in this tab and puts it on the device as one run (`MapRun.sendToDevice`). The build makes exactly the map of `nextMap` or nothing: when a region, a box or a map style of it is not there any more, the build ends with one sentence, as it does for an area with no map data, a refusal of the memory check and a failed memory check. Stop and a pulled cable also end each wait before the run. While the build runs, the browser asks before it closes the tab.

After the put, `sendMap` remembers the map object with its area and its colours (`built` of the remembered device), and sets `nextMap` to `null`. The build sends the colours that the two map styles have at that moment and gives their versions, so `built` names what is on the device, also when a style changed after "Done". When the rider chose another map during the build, that map still waits. A send that does not end keeps `nextMap`, and the card keeps its old map, because the device replaces the old map only at the end of the put. The next send downloads the cells again. After the last byte the device stores the map, and Stop is not available any more. A card with no room for both maps refuses the put.

The run holds the Web Lock `obc-map-work` ([`workBarrier.ts`](../../builder/web/src/lib/cells/workBarrier.ts)) while it uses the working files of map assembly in the browser storage. A run in another tab takes the same lock, so two runs do not delete the files of each other. `deviceSync.map` gives the step of the send and its percent; `wait` means that another map build holds the lock.

## Device page

The page `#/device` ([`Device.svelte`](../../builder/web/src/pages/Device.svelte)) shows the remembered device and the device sync. "Sync" means that routes go to the device and rides come from it; "update" means only a software update. The page does not run a step of the sync itself. It opens the one device session of the tab (`deviceHolder`), and the sync uses the same session, so the tab has one link to the device. The first state that applies shows:

| State | When | The page shows |
| --- | --- | --- |
| Cannot | The browser has no WebUSB. | That the cable works in Chrome and Edge, and what works here. No button. |
| Connected | The remembered device is `ready`. | The name, "Connected", "Disconnect", the live drawing, and one card of rows: Sync, Routes, Rides, Memory card, Map and Software. |
| Not connected | A device is remembered. | The name, "Not connected", "Connect", the dim drawing, the last sync, the routes that wait for the device, and the row Map. |
| Never | No device is remembered. | "Connect a device", and a note that the product works with no device. |

The row Sync shows the time of the last sync (`at` of the remembered device) and what the last sync of this page did (`deviceSync.report`). "Sync now" and, after a problem, "Try again" call `deviceSync.run()`. The row Routes counts the routes on the card and names the routes of the library that are on the device: their `sent` entry names this card and has a `key` (`allOnCard`). "and 3 more" counts the routes on the card that these entries do not name; a day in `gone` is not on the card. The row Sync says "1 route sent" or "1 route removed" for a route of one day, and "1 trip sent" or "1 trip removed" for a plan of several days. The row Rides counts the rides of the library that came from this card, from `library.rides()`, because a ride record names its card and the library has no index of it. The memory card bar shows only the used parts, because the cable does not report the size of the card.

The row Software ([`Software.svelte`](../../builder/web/src/pages/device/Software.svelte)) compares the version that the cable reports with the published one (`firmwareCheck`). "Update" sends the package to the card (`stageFirmware`) and asks the device to install it (`armUpdate`). The row says that the device installs it only when the device agreed. The firmware refuses that step today, and the row says so in one sentence.

The row Map shows the name of the map on the card. When the library state `nextMap` holds a map that waits for the device, the row shows "New area" or "New colours" and the size of its download. It is "New colours" when the map on the device has the same regions and boxes (`deviceArea`, `sameArea`). The page loads the regions of the map catalog for this comparison, one time, and only when a map waits. With a connected device the row has the button "Send the map", which starts the map send. In a browser that saves data (`navigator.connection.saveData`), the button first asks in a window. While the send runs, the row shows one line ("Download 40 %", "Build", "Send 60 %", or "Waits for another map build") and one bar in the place of the link, and "Stop" in the place of the button, so the row keeps its height. "Disconnect", "Sync now" and the software update are not available during the send. After a send that did not end, the row shows the map that waits again and one sentence under it: quiet after Stop, as a problem after a pulled cable or a card with no room. The sentence goes when the rider chooses another map. The link "Change the area of the map" opens the map area page.

A Connect button calls `requestDevice()` in the click, and remembers the device when it is `ready`. When another device is `ready` on the cable, the button names it and remembers it with no chooser, because a second chooser would open a second link to it. A device whose card has no format cannot be remembered, and the sync does not run with it; the page says that the card needs a format and has the button "Format" in the place of the Connect button. With a connected device, the row "Memory card" has the same button. "Format" asks in a window first, which names the device, because the format (`client.format`) erases the map, the routes and the rides on the card. The device restarts after its answer, so the page says "Formatting" until the link goes; the device then connects again with an empty card. The window keeps the device and the card of the moment it opens, and closes when another device or card is on the cable, so a format never goes to another card. A format that fails shows one sentence, until the link goes. "Disconnect" frees the device for another page; the sync takes it again at its next `ready`. The error of a device that another page holds is one plain sentence.

The drawing ([`Drawing.svelte`](../../builder/web/src/pages/device/Drawing.svelte)) is the device as the iOS app draws it. Its screen shows a sample map in the catalog skins `default` (Day) and `dusk` (Night), with `openLiveSkinPreview` of map style. The preview draws 240 × 240 pixels, so the page adds the lower 80 rows of the 240 × 320 screen from a second frame with the camera moved down.

The top bar shows a chip with the name of the remembered device: a hollow dot, or a green dot while it is connected. While a sync runs, a sync icon turns beside it. After a problem of the last sync, the icon is a button that starts the sync again.

`planner.html?fake-device` puts the wasm test device on a pretend cable ([`fake-device.ts`](../../builder/web/test-support/device-sync/fake-device.ts)), with `window.deviceTest`. The dev server has it, and the build of the browser tests has it through `VITE_FAKE_DEVICE=1`. Another build has no path to it.

## Map area page

On the page `#/device/area` ([`Area.svelte`](../../builder/web/src/pages/Area.svelte)) the rider chooses the area and the colours of the device map. The page opens with the map that waits (`nextMap`), else with the area of the map on the device, else with no area. `deviceArea` ([`area.ts`](../../builder/web/src/lib/device-sync/area.ts)) knows the area of the map on the device in two cases: this browser sent the map (`built` of the remembered device names the map object on the card), or the map has the name of one region of the map catalog.

The page shows the coverage map of map assembly (`CoverageMap`) with no tool rail. The switch "Countries and regions" / "A box" of the left card sets the tool of the map: a click adds a region, a drag draws a box. The ground outside the area is grey and a little pale, with its names and lines at full contrast, because the rider reads them to choose what to add. One line goes around the area, and each route of the library is a line in the colour of a route. The lines of the map cells show faintly where a cell is at least 36 pixels wide: an area grows to whole cells, and the lines show why. While the rider draws a box, a line goes around the cells that the box takes. The left card lists the parts of the area, each with a button that removes it.

`routesOutside` ([`outside.ts`](../../builder/web/src/pages/area/outside.ts)) checks the routes that wait for the device and the routes on the card of the remembered device. For each route it gives the length of the summary line outside the detail cells of the area. Ground with no map data in the catalog does not count, because the rider cannot add it. A route with no length outside the area gets no warning. For each other route the card offers two answers: a box around each part outside the area, and the smallest region of the catalog there.

"Colours" opens the choice of the map styles of map assembly (`SkinStep`) in a window. "Edit the colours" opens the colour editor of map style over it, which saves a style of the rider in this browser; `nextMap` holds its id as it holds the id of a ready-made style. "Delete" asks in a window before it removes a style of the rider. When the map data or the elevation data lacks a part of the area, the card says so, and it says nothing else about the data. The credits start closed behind the "i" button of the map. The button opens the credit of the base map and the credits of the data of the device map, with a link to the licence of the map data, together. The card shows the size of the download of the whole map and the size of the map on the device. "Done" gives `nextMap` the regions, the boxes, the two style ids with the versions of the styles (`areaOf`) and the size of the download, or `null` when the map is the map on the device or has no part. An edit of a style of the rider keeps its id and raises its version (a save with no change keeps the version), and `sameMap` compares the versions, so new colours of a style that is on the device make a map wait. A version that is not known, as in a map from before the versions were kept, counts as the same. It writes only a value that differs from the stored one. The page needs no remembered device, and nothing on it builds a map.

## Covers

A cover is one TrailView still image of a route or a ride, 1920 × 1280 pixels, with the place of each point of the summary line in the image. The library keeps it in its store `covers`. The page draws the line from that list of points, so one cover serves each size of box.

The cover job ([`job.ts`](../../builder/web/src/lib/covers/job.ts)) starts after the first page shows. It listens to the library. After a save of the planner's route, the job asks for its cover 30 s after the last change, so several saves in a row give one cover. A page asks for a cover with `wantCover`. The job keeps the 12 newest asks of rows that wait, so a scroll through a long list starts few renders; a row that comes into view again asks again. An ask of a card, of a page or of the job itself always waits. The job renders one cover at a time in the whole browser: it holds the Web Lock `obc-cover` for each cover, and reads the record again inside the lock. It renders only while the page is visible and online, and not while a TrailView window is open. When a TrailView window opens, the job stops the render and does it again later. A record gets the state `failed` after three tries. The job does not run when the browser asks to save data, and an ask then does nothing. Covers are off when the browser has no WebGPU or a coarse pointer (a phone), so a card there shows the map picture and a row asks for nothing, and for the rest of the session when the job finds a software renderer or a still that reached its time limit.

A card whose record gets no cover shows a still picture of the map ([`map-picture.ts`](../../builder/web/src/lib/covers/map-picture.ts)). The job makes it for the ask of a card: when covers are off or after the cover of the line ends `none` or `failed`. The picture is the planner map with no text, icons or contour lines, 768 × 512 pixels, in the theme of the page. An offscreen MapLibre map draws it, and the job loads that code only for the first picture, so the shell does not load MapLibre at its start. The record of `covers` keeps the picture in its field `map`: one image for each theme, the place of each point of the summary line, and the credits of the map data. A picture waits as a cover does, but not for TrailView. The job makes no more pictures for a line after `none` (the line is outside the map data) or after three failed tries. A done cover removes the picture.

The cover part ([`Cover.svelte`](../../builder/web/src/lib/covers/Cover.svelte)) loads the record and its cover from the library and gives the image to the picture part ([`CoverPicture.svelte`](../../builder/web/src/lib/covers/CoverPicture.svelte)), which draws it. The picture part cuts the image as CSS `cover` does, and moves the cut toward the middle of the route. It draws the line thinner far from the eye, and draws no part of the line that the terrain hides. It shows a selected part and a mark, and gives the point of the line under the pointer. A row and a card show a start dot of 10 px at the first point of the line, in the line colour, on a cover where that point is visible and on the plain line; the page of a route or a ride shows its own pins. The picture of a trail has none. The prop `place` of the cover part tells where it shows: `row` and `page` ask for the cover, and `card` asks for the cover and then the map picture. A row and a card show a stored map picture of the record. Only a record with no cover image reads the theme, because a cover does not depend on it. With no cover, a row or a card shows the map picture of the theme with the line drawn on it as on a cover. Else the part draws the summary line on a plain ground. `planner.html?cover=ID` shows the cover of one record in a home card and at a large size, for the browser test.

The covers of signed routes come from a published set ([route-pictures.md](../../specs/route-pictures.md)), not from the cover job. [`route-pictures.ts`](../../builder/web/src/lib/covers/route-pictures.ts) reads the live manifest on the host of the planner catalogue once, and the cell file of each cell once. A read that fails for a reason other than a 404 is not kept: the manifest is read again at most once in a minute, and a cell file at the next request. A route has a cover only when the key in its cell file is the key of its line, so a changed line shows no cover. A cover file that answers 404 reads the manifest again, at most once in a minute. The picture of a row or a card ([`SignedPicture.svelte`](../../builder/web/src/pages/explore/SignedPicture.svelte)) loads the cover when it shows, and draws the line on it in the colour of the route with a white glow. A row shows the row image of the cover, half the size of the full image, and the card the full image. Two pictures of one route and one size share one load and one bitmap (`holdCover`), so a card that opens from its row shows the line on a plain ground until its full image is there. When the last picture of a route and size goes, its load stops and its bitmap closes. A row shows its picture only near the view, so a long list holds few bitmaps and a fast scroll loads few images. While a cover shows, the map shows the credits of the set with its own.

The window "Add files" ([`AddFiles.svelte`](../../builder/web/src/pages/AddFiles.svelte)) adds GPX and FIT files, folders and the ZIP exports of services to the library. It gives the file readers of the shared core to the library (`readFiles`), so that the library depends on no other system. A route from a file becomes a plan of the planner with one drawn leg (`planFromFile`). The library gives the JPEG and HEIC files after the tracks; the window finds the ride of each photo among the stored rides and the rides of the files (`photoRide` of [`photos.ts`](../../builder/web/src/lib/ride/photos.ts)). It reads the file of a ride only when the start, the end or the bounds of the ride can hold the photo, and of two rides that fit, the earlier one wins. A photo that fits no ride is named in one line and not added; a photo of a ride that the browser cannot open is not readable. The Routes page opens the window.
