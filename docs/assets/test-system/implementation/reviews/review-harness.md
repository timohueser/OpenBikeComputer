# review:harness — Architecture feasibility of the two harnesses (§2.3) and the relocation of obc-app's inline system tests (§2.4)

## verdict
The seams the plan builds on are real, but the plan skips three structural facts that change its shape: (1) putting `Device` in obc-host-core and consuming it from obc-app's own tests/ creates a dev-dependency cycle that makes every `cargo test -p obc-app` compile obc-app twice plus obc-host-core, which works against the inner-loop goal; (2) the conformance corpus cannot run over HostLoop as-is, because HostLoop deposits outcomes inside `execute` and the corpus's answer-cadence lives in the trace runner, so "CoreHarness deleted" requires a production split of the reference executor plus fault-injecting stores and a scripted planner; (3) the board row promises a "policy-free RideExec core driven by Device", but what is extractable without the rejected async extraction is ~60 lines of wake/feed/GPS predicates, and they replace almost none of soak A–K. The relocation risk statement is honest in tone but the count is wrong: roughly a third of the 289 tests are unit tests by the plan's own definition and must stay inline, and the dominant private access is Navigator seeding (85 `route_state_mut` writes), not `app.ui.*` reads.

## must_fix
- **[§2.3 A + §2.4 obc-app row (Device in obc-host-core; obc-app tests/main.rs over Device)]** A dev-dependency cycle is created and never mentioned. obc-host-core depends on obc-app; obc-app's integration tests would dev-depend on obc-host-core. Cargo accepts this for integration tests (obc-app's lib is built once, non-test, and shared), and the plan's split (inline unit tests stay in the lib target, scenarios move to tests/) does avoid the two-instance type-identity problem — but only as long as no inline test ever imports obc-host-core. What remains is cost: every `cargo test -p obc-app` (even `--lib`) now builds obc-app as a normal rlib for obc-host-core AND as the test crate, then builds obc-host-core (dispatch 1,096 + trace 732 + stores + flat_map/flat_routes + obc-replay + obc-storage std + obc-link) before linking. That is on the exact path the plan wants to take from ~72 s to 'seconds'.
  evidence: host/obc-host-core/Cargo.toml:11 `obc-app = { path = "../../firmware/obc-app" }` (normal dep). firmware/obc-app/src/lib.rs:18 `#![cfg_attr(not(test), no_std)]` (the shared instance is the no_std lib; the test crate re-enables std). firmware/tools/check_dependencies.py:5-6, 55-56 skip `kind == "dev"` — the rules script would allow the edge, and dependency_rules.json's 'app must remain host-independent' is not consulted for dev edges. cargo tree -p obc-host-core -e normal = 81 nodes (no heavy native deps, so the pull is compile time, not new toolchains). Plan lines 141-153 and 178 place Device and the tests as described and do not name the cycle.
  change: Decide the crate boundary explicitly and measure before committing: either (a) accept the cycle and record `cargo test -p obc-app --lib --no-run` before/after adding the dev-dep (a five-minute experiment, belongs in Sequencing step 1), or (b) put the relocated scenarios in the crate that owns Device (obc-host-core/tests/ or a new host/obc-device-tests) — no cycle, no double compile, `nextest -E 'rdeps(obc-app)'` still selects them on an obc-app edit; the price is that `obc test -p obc-app` no longer runs them (the plan's own `obc test system` does). State which one and why.
- **[§2.3 A ('answers with a chosen cadence — RunnerMode already exists') + §2.4 obc-host-core row ('conformance corpus over Device, CoreHarness deleted')]** RunnerMode exists, but the delay is applied by the trace runner between `TraceHarness::run_pass -> Vec<Outcome>` and `TraceHarness::deliver(outcome)`. HostLoop has no such seam: `execute` serves every effect and deposits the outcome into its own inbox in the same call. To run the corpus over HostLoop you must split `execute` into serve→outcomes and deliver — a change to the shipped reference executor made for a test (the plan's §3 lists exactly two L13 exceptions and this is not one). The corpus also scripts what HostLoop computes for real: nav-plan answers, DFU scan/install results, settings results, a failed finalize, a partial append, a catalog read that fails once, a removal the store refuses — HostLoop needs a real `Reader` + elevation source per scenario and the Mem* stores have no fault knobs. And what the gate proves changes: today the two runners differ only in cadence over a policy-free executor; over HostLoop a HostLoop bug fails both columns identically and the differential is gone.
  evidence: host/obc-host-core/src/trace.rs:399-407 (TraceHarness: run_pass returns Vec<Outcome>, deliver is separate), :479-530 (run_scenario_seeded applies DelayedQueue between them). host/obc-host-core/src/dispatch.rs:360-388 (`execute` requires `reader: &obc_reader::Reader`, `elev`), :391-420 and :738-745 (`deliver` writes straight into `self.inbox.outcomes`; debug_assert on a full slot). host/obc-host-core/src/stores.rs (MemRideStore/MemTrackStore: no failure knobs). host/obc-host-core/tests/device_core_corpus/mod.rs:341-389 (CorpusState: pending_nav_plan, pending_dfu_scan, pending_dfu_install, pending_settings_result, fail_next_finalize, partial_append_once, catalog_read_fail_once, route_delete_fail_once). host/obc-host-core/tests/device_core_conformance.rs:1-13 ('differ only in what runs the frame'), :231-260 (CoreHarness holds CorpusState). dispatch.rs:66 `feed_routes(app, routes, trace: &mut dyn TraceSink)` is the one trace hook HostLoop already has.
  change: Either keep CoreHarness (535 LOC) and shrink only its duplicated fakes (ScriptedFix, EVERYTHING → the shared ScriptedPorts / PlatformSupport::ALL, ~100 LOC), dropping the −530 claim; or state the production change honestly as a third L13 exception: split HostLoop::execute into `serve(..) -> Outcomes` + `deliver(..)`, add fault-injecting repository wrappers and a scripted-answer path for navigation/DFU/settings, and accept that the gate then proves DeviceCore+HostLoop rather than DeviceCore alone. Put this as an owner decision in §5; it is not a detail of step 3.
- **[§2.3 B ('To verify before building: that Ceilings/Policy/OpenPolicy in engine.rs cover every MockDeviceOptions knob')]** Two of the three names are in the wrong file and, more importantly, the knob mapping is not a 'verify later' item — three of the nine TS knobs are not engine properties at all. Busy, noSpace-with-bytes-required, paged LIST with a staleness-checked cursor, compare-and-swap on replace, bilateral cancel and link-lost ARE in the engine. `deviceInfo` (firmware/hardware/serial — used by 4 test files) is the vendor lane, outside protocol v4 and outside obc-link entirely. `faults` (asserted empty in 4 files) is the TS mock's own exception log — meaningless for Rust; those assertions go. `commitSequence`/`storeId` are set directly on the mock (15 and 44 lines across 7-9 files) but in Rust come from the formatted card and advance by seeding — tests asserting exact sequences must be rewritten relative. `armPolicy: allow` needs a custom `Policy` impl in the wrapper (OpenPolicy refuses). `pageEntries` is only reachable indirectly via the control ceiling. `formatRecovery: 'catalog-unreadable'` needs a torn superblock, not a knob. `sinkUploads` is used by no test.
  evidence: firmware/obc-link/src/flat/store.rs:184-221 (Policy trait: accept / validate_package / hand_off; OpenPolicy refuses ARM). firmware/obc-link/src/flat/engine.rs:147-161 (Ceilings control/stream), :32 and :1022/1095 (busy), :1641-1645 (NoSpace with `required` context), :954-968 (LIST cursor + sequence staleness), :405 (CAS 're-checked immediately before the commit'), :920-936 (cancel_live), :904 (link lost). builder/app/src/lib/usb/loopback.ts:316-345 (the 9 options), :373-375 (`faults`, `requestLog`), :400-444 (seed/entries/payloadOf/sequence). Grep across builder/app/src/**/*.test.ts: storeId 9 files/44 lines, commitSequence 7/15, deviceInfo 4/7, faults 4/5, pageEntries 2/4, streamPayload 3/7, cardBytes 2/3, armPolicy 2/3, formatRecovery 1/1, sinkUploads 0. builder/app/src/lib/usb/pipe.ts:12-31 (DeviceLink carries a `vendorIn` lane beside control/stream).
  change: Replace the 'to verify' sentence with a nine-row knob table: engine-native (busy, noSpace, cursor, CAS, cancel, link-lost, cardBytes, streamPayload, formatRecovery=unformatted), wrapper-added (armPolicy=allow via a Policy impl; deviceInfo as a 10-line vendor-lane stub; requestLog if any test needs the opcode trace), and dropped (faults assertions, sinkUploads, exact commitSequence/storeId literals → relative assertions). Fix the file citation to store.rs.
- **[§2.3 B (2) stdio process + ProcessTransferLink for Swift; §2.7 iOS lever; §2.8 deletions]** Two bindings of the same Rust core are proposed at once (wasm-bindgen for TS, stdio process for Swift), and the two source surveys disagree on the Swift half without the plan saying so: the web-desktop survey recommends Swift stays on its scripted actors ('loading wasm from Swift is more machinery than it saves; revisit as a C-ABI staticlib only if a phone-side conformance gap is measured'), the iOS survey recommends the process. On the Swift side the deletion is 374 LOC of actors in five tests; the replacement is ~100 (ProcessTransferLink) + ~200 (new suite) + a framing contract + a Rust build inside ios-unit, which today is checkout + `swift test` with no Rust toolchain step. Net Swift LOC ≈ 0 and the ios-unit job gets slower, on a plan whose iOS lever is 'make iOS faster'. Foundation.Process from `swift test` is workable (the desktop macOS job already shows the toolchain recipe: actions-rust-lang/setup-rust-toolchain + Swatinem/rust-cache), but it is a cold cargo build of obc-link + obc-storage(std) + the binary on every macos-26 run unless cached, and a second glue layer to maintain. A C-ABI staticlib is not simpler (SwiftPM binaryTarget/xcframework per arch).
  evidence: survey-web-desktop.md line 97 vs survey-ios.md lines 106, 118, 127. companion-ios/Packages/OBCKit/Tests/OBCProtocolV4Tests/TransferClientTests.swift:96,228,273,352 (four actors, ~374 LOC, 5 tests; survey-ios.md:28). .github/workflows/ci.yml:851-872 (ios-unit: no Rust step), ~1088-1095 (desktop macOS leg installs Rust via setup-rust-toolchain + rust-cache). grep 'Process()' in companion-ios/Packages/OBCKit/Tests returns nothing today. companion-ios/.../OBCProtocolV4/TransferClient.swift:7-16 (TransferLink: 8 async record calls — the seam is fine). Plan line 164 counts 'delete the scripted actors' as a win; plan line 236 counts ios-unit time as a lever.
  change: Commit to one binding in the epic, chosen by consumer: (a) process over stdio with two length-prefixed lanes — usable from vitest (Node child_process), Swift and Python with one framing contract; add wasm only if the manual browser dev-harness must keep a simulated device; or (b) wasm first for TS/browser and leave Swift on its actors until a phone-side conformance gap is measured, as the web-desktop survey said. If Swift is included, the ios-unit job must gain setup-rust-toolchain + rust-cache and the plan must show the measured job time going up, not down. Recommendation: (a), because it is one artifact, and the dev-harness is manual-only today.
- **[§2.4 board crate row ('policy-free RideExec core extracted to host-compilable code … driven by Device') and §2.8 row 2 ('the board-executor host suite replaces what A–K proved on the host side')]** Overpromised. RideExec is a data struct (outcome/fact/need/effect slots, one in-flight removal, nav token, arm counter) with `owed()` (one boolean expression), `polling_store()` and `deliver()`. The other named pieces are tiny pure predicates: desired_gps_power is 8 lines, the WDT feed predicate is 2 lines, the wake fold is ~12 lines over local flags. The phase order (guard split, bulge-first, arena claim/release, Ticket/Reply round trip to the storage task, present-then-arm) is the 2,400-line async `run_app` body — moving that is the async extraction #1262 rejected (prior extraction inflated stack ~5 KiB). The obc-display precedent is a data/contract split (row-hash, wire pack, Presenter trait) with the DMA transport left on the board; it is not an executor split. 'Driven by Device' is a category error: Device = App + HostLoop; RideExec is the board's replacement for HostLoop, not its client. And the ~60 extractable lines do not reproduce soak A (arena ×50), B (USB interlock), E (removal under backpressure), F (one commit = one refresh), G (phone), H (recorder close) — at most J (wake/pace) and the GPS/WDT predicates.
  evidence: firmware/obc-fw-nrf54l/src/ride.rs:641-735 (RideExec struct + owed/polling_store/deliver), :741-751 (desired_gps_power), :1071-1080 (WDT feed gated on INPUT_HB_MS age), :3125-3152 (wake fold: animating/polling_store/immediate/owed → next_ms, WDT_FEED_CAP_MS, MAP_XFER_PACE_MS), :788-830 (run_app signature: MapDisplay, SharedStoreMutex, FlatStore, arena nav, WatchdogHandle, SensorConsumer/Control) — 13 embassy uses in the file, no lib/test target in the crate. issue-1262.md:52 ('Do not mechanically extract async functions'), :103-107 (extraction-first rule: move pure decision logic to a host-testable crate), :179 (prior extraction +~5 KiB stack). firmware/obc-display/src/display_contracts/presenter.rs:47 (Presenter trait), Cargo.toml (no embassy; `conformance` feature for test-only checks). host/obc-host-core/src/dispatch.rs:206-210 (the residual predicate already moved into obc_app::device_core::residual so board and host check the same rule — the existing pattern for board-shared decisions).
  change: Reword the row to what #1262's amendment already allows: extract the four decision predicates (next-wake fold, WDT feed gate, desired_gps_power, owed) as pure functions into obc-app next to `device_core::residual` (or obc-platform), unit-test them there, and re-wire ride.rs to call them — no traits needed, no Device involvement, ~60-80 LOC moved, zero stack change (they are already synchronous). State that the RideExec phase order stays on the board with #1262's physical evidence, and drop the claim in §2.8 that this suite replaces A–K; the host half of A–K is the corpus under BOARD_SUPPORT (already listed) plus these predicates; A/B/G stay physical.
- **[§2.4 obc-app row + §1.3 item 3 ('the 289 relocated scenarios'; 'medium-high risk, some assertions rewritten or dropped')]** The risk tone is honest; the count and the named cost are not. About a third of the 289 are unit tests by the plan's own definition and cannot move: screens.rs has 34 tests that hand-build AppState/Activity/RecorderMachine and drive `screen::apply` through `test_ctx` (screen tests 'via Ctx' — §2.4 says those stay inline); pass.rs's 32 stage-order/wiring tests are about private stage order (the survey says keep them inline; the plan counts them as relocated); ~40 of app.rs's tests are AppState/course/compass/altimeter/clock unit tests that construct `App::new` or bare `AppState` and read machine internals. ## should_consider
- **[§2.3 A (Device home = obc-host-core, a production crate of obc-sim and obc-web-demo)]** ScriptedPorts, Frame, Script/Step and the seeding presets would ship in the obc-host-core rlib that obc-sim and obc-web-demo link unless gated. obc-display already solves this with a `conformance` feature turned on by a self dev-dependency; reuse that pattern (`testing` feature) so the harness never reaches the web demo's wasm bundle, and so 'scaffolding dies with its purpose' has a switch.
  evidence: firmware/obc-display/Cargo.toml:14-22 (feature `conformance`, self dev-dep enables it for test targets only). cargo metadata: obc-host-core is a normal dependency of obc-sim, obc-bench, obc-usb-host, obc-web-demo.
- **[§2.3 A (every obc-app scenario over Device)]** HostLoop::execute requires a loaded map (`reader: &obc_reader::Reader`) and an elevation source for every pass, so every relocated scenario pays a map build even when it never touches the map. Either keep a map-free fast path (a `Device::without_map()` that serves effects but answers navigation/derived needs with scripted results) or accept the build_min_obcm cost per test and say so; fold build_min_obcm into obcm-testkit as the survey suggests.
  evidence: host/obc-host-core/src/dispatch.rs:360-372 (execute signature). firmware/obc-app/src/harness/support.rs:108-225 (build_min_obcm, ~120 LOC, hand-built OBCM bytes).
- **[§2.3 A ('answers with a chosen cadence')]** Say plainly that the cadence parameter applies only to the conformance runner (TraceHarness), not to the relocated obc-app scenarios, which would run Immediate over HostLoop unless the execute split from must-fix #2 is done. Otherwise the reader assumes 289 tests gain the delayed-answer property for free.
  evidence: trace.rs:140-146 (RunnerMode), :479-530 (only run_scenario_seeded consumes it); dispatch.rs:738-745 (HostLoop delivers immediately).
- **[§2.3 B ('Verified: … builds for wasm32 today')]** Downgrade to 'resolves for wasm32' — the evidence is a `cargo tree --target wasm32-unknown-unknown` (pure-Rust graph, no std::fs/thread/net in sim.rs), not a build.   evidence: cargo tree -p obc-storage --features std --target wasm32-unknown-unknown -e normal: embedded-sdmmc (fork, no defaults), heapless, obc-crc, obc-formats, obc-ports, obc-link. grep 'std::(fs|thread|time|net|process)' in firmware/obc-storage/src/flat/sim.rs = none. survey-critic.md:53-55 says the same and marks the knob coverage unverified.

Both take minutes and decide must-fix #1 and #4.
  evidence: survey-build-time.md:22 (obc-app inner loop 72 s); ci.yml:851-872 (ios-unit today).
- **[§2.4 obc-host-core row ('+ BOARD_SUPPORT variant')]** This is the one cheap, real host-side proof of the board's capability shape and needs no new harness: the corpus already takes a PlatformSupport constant. Promote it out of the 'over Device' clause so it does not wait on the CoreHarness decision.
