# review:hil — Modular HIL / phone slot (owner requirement 3): does the plan's hardware tier, the "same scenario file on sim or DK" claim, the #1177 smoke-upload estimate, and the phone-in-the-loop door hold up against the wire that actually exists.

## verdict
The seams the plan names are real (debug_link K/F/A/C/H/P/R injection, the board's `input: <gesture> on <Screen>` ack, Swift `TransferLink`), so the HIL slot is genuinely modular on the phone side and on the input side of the DK. But the plan overstates it in three places: "the same scenario file runs against the sim or a DK" is false for most `Step` kinds and for every assertion class except screen name and landmark log lines; the `hardware` `workflow_dispatch` job has no runner that can reach a DK (every workflow is ubuntu-*, ci.yml says "There is no board in CI") and "DK over VCOM/USB, phone over BLE" cannot be one script because BLE is parked whenever VBUS is present; and the #1177 smoke-upload is under-estimated because its recorded pass signature ("volume set MSx committed") no longer exists in the firmware and there is no native Rust PUT sender at all. The biggest issue is Q8: the "~200-line VCOM link" is roughly one third of what `obc smoke-upload` needs, and the CI job it is attached to is speculative capability by the owner's own rule.

## must_fix
- **[§2.3 last paragraph (and the device-survey sentence it inherits: 'the same scenario file runs against the sim or a DK')]** The claim does not hold for the Device Script as seeded from dirty_parity, on either side of the wire. Input side, mapping each Step kind to a debug_link line: keys→`K`, fix→`F`, compass→`C`, hr→`H`, power→`P`, cadence→`R` (all exist); battery→none; feed(fn(&mut App))→none (in-process closure); fact(fn(&mut ExternalFacts))→none (store revision, transfer, BLE link, warnings, route/trip uploads, update result are produced by the board's own executor; the only narrow host→device commands are `N`, `dfu-install`, `ride-damage`, `ride-repair-fail`, `store-census`); weather(snapshot builder)→none; probe(fn(&App))→none. Output side: the board reads back only `input: <gesture> on <Screen>` (and only when a gesture is accepted, so a screen check needs a net-zero `K t 1`/`K t -1` probe pair), `T` render-stats telemetry, `D` DFU lines, `ui frame` timing, `flat:` catalog lines and `store-census`. There is no frame/pixel readback (#91 says so), no typed effect/outcome readback, no catalog-bytes readback. So the assertion classes Device is built on — frames/hashes, effects/outcomes, catalog bytes, ExternalFacts state — have no board equivalent.
  evidence: apps/obc-sim/tests/dirty_parity.rs:210-336 (Step fields: keys, ports, feed, fact, weather, probe, expect); firmware/obc-platform/src/debug_link.rs:9-63 (host→device lines F A C H P R K Z N dfu-install ride-damage ride-repair-fail store-census) and :64-76 (device→host T and D only); firmware/obc-fw-nrf54l/src/ride.rs:2341-2343 (`input: Step {n} on {screen}` / `input: {gesture} on {screen}`); firmware/obc-app/src/device_core/shared.rs:612-677 (ExternalFacts setters that have no wire form); #91 body 'Telemetry today is render-stats only — there is no framebuffer readback'; memory dk-vcom-injection-harness 'The board names its own screen… probe non-destructively with a net-zero K t 1 / K t -1 pair'.
  change: Replace the sentence with a scoped one: the HIL hook is the gesture+sensor subset of Script (keys/fix/compass/hr/power/cadence) plus screen-name and landmark-line assertions; feed/fact/weather/probe/frame/effect/catalog assertions are host-only by construction. If a shared scenario format is still wanted, define it as that subset (the debug_link line grammar itself, which #91 already proposed) and have Device consume it, rather than promising Device's full Script runs on a DK.
- **[§5 Q8 and §2.8 row 2 (obc smoke-upload built on a ~200-line VCOM link; #1177's evidence list)]** #1177's pass signature is stale and the sender half does not exist. (a) 'volume set MSx committed' can never appear: volume sets were retired with OBCM v14 (a map is one file); no board log contains 'volume set'. `warn_bounce` logs as 'SD: misaligned block buffer…'; no `discarded`/`overflow`/reject-probe defmt lines exist in the board crate at all (those were v2 USB link landmarks). (b) #1177's 'obc-usb-host / obc-replay … can push it over the cable' is wrong: obc-usb moves bytes only; obc-format-card does LIST+FORMAT; the desktop's usb module explicitly refuses to reimplement the protocol; obc-replay is GPX replay; obc-usb-host is an eframe GUI sensor feeder. The only PUT client in the repo is TypeScript (WebUSB, Chrome-only). So `obc smoke-upload` = VCOM link (~150-200) + landmark assertions (~60) + assemble invocation (~30) + a native PUT sender that has to be written (~350-450 Rust modelled on obc-format-card.rs with obc_link::flat record codecs) — roughly 600-700 LOC, not ~200.
  evidence: firmware/obc-storage/src/flat/source.rs:33 ('A map is one file now'); grep 'volume set' over firmware/ and host/ hits only comments (obc-ble descriptor.rs:114 'retired', obc-app screen/map_transfer.rs:55, obc-reader/mod.rs:441); firmware/obc-fw-nrf54l/src/card_io.rs:18-24 (the bounce warning text); grep of firmware/obc-fw-nrf54l/src for defmt 'discard|reject|overflow' returns nothing; host/obc-usb/src/lib.rs:1-5 ('Everything here moves bytes'); host/obc-usb/src/bin/obc-format-card.rs:1-35 (LIST/FORMAT only, 461 LOC); apps/obc-desktop/src/usb/mod.rs:9-15 ('The protocol is not reimplemented here'); host/obc-replay/Cargo.toml:6; host/obc-usb-host/src/main.rs:326 (eframe main); builder/app/src/lib/usb/client.ts 1,249 + protocol.ts 1,129 + records.ts 264 LOC (the only PUT client).
  change: Restate #1177's deliverable against current landmarks before it is cited as the hardware job: pass signature = `flat: catalog holds … map object(s)` (flat_store.rs:1401) and `flat: map object … open` (1632) after reboot, absence of `MAP UNREADABLE` (1656) and of `SD: misaligned block buffer`, plus a `store-census` before/after. State the two halves and their LOC in Q8 (link ~200, native PUT sender ~400) so the owner is deciding on ~600-700 lines of Rust, not 200. Replace 'include one shard whose length is an exact multiple of 512' with 'one map file whose length is a 512-multiple'.
- **[§2.2 hardware tier row and §2.5 '`hardware`: one `workflow_dispatch`-only job whose command is the HIL script']** A CI job cannot run this: every workflow in the repo runs on GitHub-hosted ubuntu runners, there is no self-hosted runner, and ci.yml states there is no board in CI. A dispatch job with no runner that can reach a DK is a job that can only fail — it is exactly the 'provision for operations that have never happened' the owner's rule forbids, and the registry's `hardware` level already sat unused for 25 days for the same reason. Separately, 'DK over VCOM/USB, phone over BLE' as one tier/one script is impossible: the board parks the BLE radio whenever VBUS is present, so cable and phone sessions are mutually exclusive, and the phone path has no CoreBluetooth seam to script.
  evidence: grep 'runs-on' .github/workflows/*.yml → ubuntu-latest / ubuntu-24.04 only, no self-hosted; .github/workflows/ci.yml:17 'There is no board in CI, so every embedded target is build-only'; tools/suite_registry.py:28,537 (hardware level defined) with survey-infra.md:10 'live/hardware 0'; memory dk-vcom-injection-harness 'BLE is parked whenever VBUS is present … run every cable scenario before every phone one'; survey-ios.md no_hil_story (BLETransport has no injectable CoreBluetooth seam).
  change: Make the hardware entry point a local `obc` recipe next to `obc flash`/`obc rtt` (tools/justfile:117, 208), documented in the board README, with no CI job until a bench runner exists (then it is one job file, as survey-infra already says). Split the row into two manual recipes: 'DK over VCOM+USB' (the smoke-upload/landmark script) and 'phone over BLE' (a Mac or iPhone running BLETransport against a DK with VBUS off, re-running the Swift conformance suite) — never the same script.

- **[§5 Q8 harness language (Python pyserial vs Rust)]** Recommend Rust for the single hardware entry point: obc-usb-host already depends on `serialport = "4"` and on `obc_platform::debug_link` (`format_fix`, `parse_telemetry`), so a Rust harness reuses the shared codec with zero wire drift — #91's original argument — and the PUT sender must be Rust anyway (obc-usb + obc_link::flat codecs are Rust; the TS client only runs in Chrome). The RTT plane stays a log-file tail from `obc rtt | tee` (no probe-rs crate is in either Cargo.lock), which is fine in either language.
