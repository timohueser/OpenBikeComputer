# review:rules — owner rules, locked decisions, rejected proposals, taste

## verdict
The plan's shape (one virtual device, cargo as the Rust registry, four tiers, fewer binaries) is consistent with the owner's rules and the §3 table is the right instrument, but §3 is not yet honest: it says R1–R19 are not re-proposed while §2.7 re-proposes the rejected SHA-256 length seam and the payload shrink that #1502 refused in writing, it says L13 is kept "with one exception" while naming two and adding at least four more production changes for test speed, and it omits three locked decisions the plan overturns (L11 exception bookkeeping merged one day ago, L19 timing shape, the 2026-09-12 #1262 "no further extraction" disposition). The biggest single issue is the board row in §2.4: it schedules a structural extraction of ride.rs that #1262 explicitly de-defaulted and that L21 says must be measured on hardware after every step, inside a plan whose premise is no hardware.

## should_consider
- **[§2.2 Tiers]** By the plan's own principle ('a tier exists only if it changes when or how a suite runs', :109-110) `unit` and `system` are the same tier: both run 'every affected change'. Say what mechanically separates them — unit = the lib target, system = the crate's single `tests/main.rs` target that may sync fixtures and carries the 60 s budget — or collapse to three tiers (pr / heavy / hardware) and make 'system' a naming convention for the tests target. Otherwise this is the R9 boundary (#1449 refused to litigate unit vs component) under a new name.
  evidence: plan-draft.md:124-129 (both rows 'every affected change'); survey-plans-decisions.md:42 (R9).
- **[§2.5 `hardware` job and §2.2 hardware tier]** Registering a `workflow_dispatch` job 'whose command is the HIL script' when no such script exists (#1177 never built; no 'smoke' recipe in tools/justfile) is provisioning for an operation that has never happened — the owner's speculative-capability rule. Keep the tier as a documented slot and create the job in the PR that lands the first script.
  evidence: plan-draft.md:129, :204, :327-328; survey-plans-decisions.md:105-106 (#1177 'Does not exist'), :150-151 (#91 deliverables absent); memory speculative-capability-rule.md ('we have never done that' = delete signal).
- **[§2.3 B — 'OBCMock stays for the simulator app and dev panel']** This keeps a 2,738-line hand-written device (companion-ios OBCMock sources, grep) beside the new virtual device, which contradicts §2.1 'Test fakes that re-implement product policy are deleted, not maintained' and is written as an apologetic accepted cost. State it positively — 'OBCMock is the simulator app's scripted UI device and must not model the wire protocol; protocol behaviour comes only from obc-flat-device' — and name what OBCMock loses (its transfer pacing/protocol half) so the two do not diverge again.
  evidence: plan-draft.md:112-113, :165-166; survey-ios.md:56, :97; find companion-ios -path '*OBCMock*' → 2,738 LOC.
- **[§2.9 Goldens — curated ~30 frames]** Dropping 287 of 317 pixel digests removes assertions; L12 needs the replacement named honestly. `dirty_parity` compares render-every-pass against render-on-demand of the same renderer — a shared rendering regression passes both — so it is not 'the pixel oracle' for the dropped frames. Either say the curated set is a taste decision (churn 19×/21 days is the reason), or keep the digests and fix churn with the OBC_UPDATE_GOLDENS convention alone.
  evidence: plan-draft.md:48 (dirty_parity definition), :272-275; survey-plans-decisions.md:18 (L12).
- **[§2.6 The glance view vs L10]** L10 (#1600/#1611/#1654, merged 2026-09-12) says result artifacts are tool-native only, 'no converter'. A summary table read from JUnit is a reader, not a converter, but 'obc test affected prints the same table locally' implies generating JUnit locally. State that nothing is stored and that the local table comes from nextest's own output; otherwise a reviewer will read it as the converter L10 forbids.
  evidence: plan-draft.md:221-225; survey-plans-decisions.md:16 (L10), :85-90.
- **[§3 row '#1495 no new test-support crates']** That rule was scoped to TS4 ('for TS4', R15; issue-1495.md:113 'no feature flag that selects between a fast and a slow form of the same test'), not a global ban, so the row overstates what is being overturned. The real bar the two harnesses must clear is the scaffolding rule: a standing harness needs a named consumer and no death trigger — which §2.3 already supplies. Say that instead; it is a smaller ask.
  evidence: survey-plans-decisions.md:48 (R15 'for TS4'); issue-1495.md:113,121; memory test-scaffolding-stripped.md.
- **[§2.1 'One integration-test target per crate' vs §3 L2 'heavy tests in named targets']** The two statements conflict for obc-wx-bake, where #1660 just split `canonical_publication` into an unconditional binary away from captured bakes. Write the rule as 'one PR-tier `tests/main.rs` per crate plus named heavy targets' so the merge does not undo #1660.
