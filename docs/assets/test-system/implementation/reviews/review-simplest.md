# review:simplest — Simplest-possible-system / YAGNI skeptic: for every element, what is the smallest thing that meets the owner's six requirements, does it already exist, and what is lost by doing nothing

## verdict
The plan's core is sound and mostly already built: consolidate test binaries, pass the selector's precision into one nextest filterset, move the 289 inline scenarios onto the sim's existing headless assembly (App + HostLoop + Mem stores), and delete dead scaffolding. Around that core it stacks abstraction that only tests use and that no measured gap justifies: a Swift stdio device process, a `Device` that also re-hosts the sim GUI, a JUnit-parsing summary table, a fourth tier plus `obc test system`, a weekly cron nobody reads, and a `hardware` GitHub job that cannot run because there is no board in CI. The biggest single defect is §2.3A/§2.4's "CoreHarness deleted, corpus over Device": HostLoop deposits outcomes inside `execute` (dispatch.rs:404-464), so the two-cadence runner (`RunnerMode::ScriptedDelay`, trace.rs:140-146, 399-407) cannot drive it without a production change to HostLoop or the loss of the property that found two bugs — the plan presents this as settled when it is a decision.

## must_fix
- **[§2.3A + §2.4 obc-host-core row ("CoreHarness deleted; corpus, runners, VisibleState kept")]** The conformance runner is executor-agnostic by design: `TraceHarness` separates `run_pass -> Vec<Outcome>` from `deliver(outcome)` so `RunnerMode::ScriptedDelay` can hand answers back late. HostLoop::execute serves effects AND deposits every outcome into its own inbox in the same call. Running the corpus 'over Device' therefore either (a) changes HostLoop's production shape (an L13 exception the plan does not list) or (b) silently drops the delayed cadence — the property that found two production bugs (§1.2). An implementer will pick one at random.
  evidence: host/obc-host-core/src/trace.rs:1-8 ('deliberately knows nothing about the executor's dispatch policy'), :140-146 (RunnerMode), :399-407 (TraceHarness split); host/obc-host-core/src/dispatch.rs:353-375 (execute) and :404-464 (deliver(&mut self.inbox.outcomes.*)); survey-device-system.md:136 and :146 already flag this as an owner decision with the saving dropping to ~-800 LOC.
  change: Either keep CoreHarness (530 LOC) as the corpus's policy-free executor and let `Device` serve only obc-app/obc-sim/sweep/dirty_parity, or add 'HostLoop::execute returns outcomes; a caller deposits them' to the §3 L13 exception list. State which in §2.3A; do not leave 'answers with a chosen cadence (RunnerMode already exists)' as if it were free.
- **[§2.3B(2) stdio process + ProcessTransferLink + Swift conformance suite (and §4 step 4)]** Adds a cross-language wire contract (two length-prefixed lanes + a fault side-channel) that exists only for tests, a Rust toolchain + cargo build inside the ios-unit job, ~300 new Swift LOC and an unsized Rust binary, to replace 368 LOC of scripted actors that test five behaviours the shared flat-store-v4 vectors already pin byte-for-byte on all three sides. No measured phone-side divergence is cited; the web survey (the other consumer) explicitly recommended Swift stay on the actors until a gap is measured. Net LOC is >= 0 and a new maintained protocol appears.
  evidence: companion-ios/Packages/OBCKit/Tests/OBCProtocolV4Tests/TransferClientTests.swift:96-463 (four actors, 470-line file); survey-web-desktop.md:97 ('Swift stays on its scripted actors for now (loading wasm from Swift is more machinery than it saves); revisit ... only if a phone-side conformance gap is measured'); survey-ios.md:118 sizes the replacement at +100 +200 plus a cargo build in ios-unit; the phone facts that matter (BLE lifecycle, CoC writes) are hardware-only per survey-ios.md:102.
  change: Cut §2.3B(2) and the Swift half of step 4. Keep the actors and the vectors. Record a trigger: 'build a Swift-facing virtual device only when a client bug is traced to actor/engine divergence'. If cross-language truth is wanted cheaply, the vectors' hand-written producer (obc-vectors) is already that seam.
- **[§2.5 `hardware`: one workflow_dispatch-only job whose command is the HIL script; §4 step 2; §5 Q8]** A GitHub-hosted job cannot reach a DK on the owner's desk; the workflow header states there is no board in CI and no self-hosted runner exists. The job would be a registered row that has never run and can never run — exactly the speculative-capability pattern the owner's rules forbid (the current registry already has `hardware` with 0 users).
  evidence: .github/workflows/ci.yml:17 ('There is no board in CI, so every embedded target is build-only'); survey-infra.md:61 (levels live/hardware 0 suites); survey-plans-decisions.md:125 (#91's HIL testrack closed COMPLETED with no deliverables).
  change: Replace with a local recipe (`obc hil <script>` / #1177's `obc smoke-upload`) that a person runs with a board attached; the HIL 'slot' is the script plus the `BlockDevice`/`Link` seams, not a CI job. Add a GitHub job only on the day a self-hosted runner exists.
- **[§2.5 'job table (~15 rows)' and 'Kept from today' list]** Nothing stops an implementer from rebuilding the registry: a `testing/jobs.toml`, a validator, `obc suites check`, per-row reasons. The plan's own principle (cargo is the registry) implies the non-Rust side is a dict of ~10 directory prefixes -> job names inside the selection script, and the Rust side is `git diff` + cargo metadata -> filterset. The '-3,300 LOC' only materialises if the replacement is that small.
  evidence: tools/suite_registry.py:633-669 (the ~50-line reverse-dep function the plan keeps); :60-78 TEST_POLICY_PATTERNS (policy edits select 25 jobs); tools/tests/test_suite_registry.py:716-830 (the 15-row change-class table); survey-infra.md:119 sizes the whole replacement at a ~120-line map + ~150-line test + 40-line aggregate.
  change: Write §2.5 as: one Python file (~300 lines total) containing (1) the prefix->job dict, (2) changed-packages->`package(a)+rdeps(a)` filterset, (3) the 5-line unknown-path error, (4) a 40-line aggregate. No TOML, no validator, no `obc suites` subcommands, no per-suite reason strings. The 15-row table test is the only test of it.
- **[§2.5 `policy` job ('one job: selection + fail-closed orphan check + the grep guards merged into one script + fixture policy') vs §2.7 'One policy job instead of nine spin-ups ... one fewer minute of wall']** Every other job `needs` the selection output. Putting the seven guards, tooling unit tests and fixture policy in the same job as selection puts them on the critical path of every PR: wall time goes UP by their duration (today selection alone is 13 s; guards are 6-13 s each, serial). The two sections contradict each other.
  evidence: .github/workflows/ci.yml:57-171 (selection then nine unconditional jobs; each gated job `needs: selection`); survey-infra.md:4 ('selection 13 s, guards 6-13 s each').
  change: Keep `selection` as its own ~13 s job; run the merged guards as one step inside `test` (they are obc-app source guards, survey-infra.md:100) or as one parallel `guards` job. Say so in §2.5.
- **[§2.4 new `host/obc-system-tests` crate (PBF -> pack -> cut -> assemble -> card -> App -> frame)]** A new crate whose dependency closure is the union of obc-pack (libGEOS), obcm-assemble, obc-host-core and obc-app — the heaviest test build in the repo and the one every rdeps selection would drag in — while §2.7 lever 2 is simultaneously trying to get GEOS out of firmware test graphs. obcm-assemble already dev-depends on obc-pack, obc-render, obc-display and obc-route for exactly this oracle; obc-host-core depends on nothing in obcm-assemble, so an obc-host-core dev-dep there has no cycle.
  evidence: host/obcm-assemble/Cargo.toml [dev-dependencies] (obc-pack 'A dev-dep only ... carries libGEOS', obc-render, obc-display, obc-route); `cargo tree -p obc-host-core -e normal --depth 1` (no obcm-assemble/obc-pack edge); `cargo tree --workspace -i obc-host-core` = obc-sim, obc-skin-preview, obc-web-demo only.
  change: Delete the 'new crate' option. Extend host/obcm-assemble/tests/oracle.rs with one test that mounts the assembled card through obc-host-core's flat store and renders one App frame. Same for the weather product->screen test: name its home crate or drop it from step 5.
- **[§2.3A `Device` scope ('obc-sim (GUI = a window over the same runner)', ScriptedPorts implementing every obc_ports trait, Script/Step builder, PlatformSupport presets, WeatherSnapshot::synthetic, Frame with count/get/hash)]** This is the general framework the owner warned against: eight components, five consumers, and a production refactor of the 3.4k-LOC sim GUI onto a test runner. obc_ports has 13 traits; tests script six (fix/hr/power/cadence/battery/compass — dirty_parity's `Ports`). The headless sim already IS the virtual device (HostLoop + Stores + HeadlessPlatform + settle) and it is the one thing not exported as a library. Also: obc-host-core ships inside obc-web-demo's wasm and obc-skin-preview, so un-gated test scaffolding there enters two products.
  evidence: apps/obc-sim/src/main.rs:757-762 (Stores), :800-866 (settle over HostLoop — the executor already serves the sweep); apps/obc-sim/Cargo.toml has no [lib] target; firmware/obc-ports/src/lib.rs:36-404 (13 traits); apps/obc-sim/tests/dirty_parity.rs:205-300 (Step/Ports: fix, hr, power, cadence, battery, compass); `cargo tree --workspace -i obc-host-core` -> obc-sim, obc-skin-preview, obc-web-demo.
  change: Define `Device` as the smallest concrete thing: move the sim's headless assembly (Stores, HeadlessPlatform, settle, NoFix/ScriptInput) into obc-host-core behind a `sim` feature (or a `host/obc-device` crate) with ~6 methods (new(map, support), keys, fix, settle, pass_at, frame, top_screen) plus the two named seeds. ScriptedPorts covers the six scripted ports only. Leave the GUI alone; leave dirty_parity's Step DSL where it is. Add a method only when a second consumer needs it.

## should_consider
- **[§2.2 four tiers; §2.5 `obc test system [--surface]`; §2.6 jobs named `<surface>[-<tier>]`]** By the plan's own principle ('a tier exists only if it changes when or how a suite runs') `system` is not a tier: unit and system both run on every affected change inside the same nextest invocation; cargo already distinguishes them as kind(lib) vs kind(test). Drop `obc test system` and the tier suffix in job names; keep three cadences (PR / heavy / hardware-local) and let 'system' be the documentation name for tests/main.rs. Prevents an implementer from building two nextest runs or two jobs over the same artifacts.
  evidence: plan §2.1 'Tiers are execution facts, not labels'; §2.2 both rows 'every affected change'.
- **[§2.6 summary table (job, tier, selected?, result, wall, tests run, slowest test) read from JUnit; `obc test affected` prints the same table locally]** GitHub's run page already shows job, result, skipped-vs-run and wall. The only additions are 'tests run' and 'slowest test', which require parsing three formats, and the Swift xunit per-case times are contention-inflated (sum 250x wall) so 'slowest' is wrong there; XCTest has none. Cut to: the aggregate prints job/result/wall from the `needs` context (no JUnit, ~40 lines). Keep the on-demand timing-diff script over nextest junit only. Drop the local table (it would force junit profiles into local runs).
  evidence: survey-ios.md:63-64; survey-infra.md:71-72 (junit artifacts uploaded, nothing reads them); tools/ci_aggregate.py:146-165 (today's 69-row table).
- **[§2.2 heavy 'scheduled (one weekly workflow)'; §4 step 2]** No test workflow has ever run on a schedule here (the one cron that exists, test-exception-health, has not run), and a weekly red run nobody is assigned to read is an alarm by another name. Start with `workflow_dispatch` only and run the heavy set as a release step (release.yml has no test steps today). Add a cron only when the owner names who reads it.
  evidence: `grep -l schedule: .github/workflows/*.yml` = bake.yml, test-exception-health.yml, wx-freshness.yml; `grep 'cargo test|nextest|xcodebuild|npm test' release.yml` = nothing; survey-plans-decisions.md:60 (three 'weekly' suites with no route).
- **[§2.3B(1) wasm `obc-flat-device` replacing TS MockDevice]** Justified only if the engine expresses the flow tests' knobs — and that can be answered now instead of deferred: cardBytes -> SparseDisk::blank(total, seed) (sim.rs:120); formatRecovery -> blank_card/formatted_card (flat_harness:54-59); armPolicy -> the `Policy` trait (store.rs:184, used by control_with); pageEntries/streamPayload -> Ceilings (engine.rs:147, control/stream record sizes — NOT a policy object as §2.3B implies); sinkUploads -> inherent; `device.faults` (flows.test.ts:100,286) needs a ~20-line refusal counter in the glue. Also: move firmware/obc-link/tests/flat_harness/mod.rs (588 LOC) INTO the new crate so there is one Rust virtual flat device, not two; and rename one of the two things the plan calls `Device` (flat_harness::Device at mod.rs:109 vs the App-level Device).
  evidence: firmware/obc-link/src/flat/engine.rs:147-150; firmware/obc-link/src/flat/store.rs:184; firmware/obc-storage/src/flat/sim.rs:120; firmware/obc-link/tests/flat_harness/mod.rs:54-59,109,189.
- **[§2.4 web row: one Playwright spec 'the real-browser smoke and the home for #1503']** Playwright is a new dependency the plan never asks the owner about; it is defensible for the one spec (the dev-harness exists and is undriven, and it is the only 'no phone/no hardware' evidence for OPFS/Worker/WebUSB). Keep it small: the PR spec uses the 72 KB fixture and must finish in seconds; the #1503 memory measurement over large inputs is a separate heavy spec, not folded into the PR one (the plan's §2.2 already puts 'real-browser smoke over large inputs' in heavy).
  evidence: `grep -c playwright builder/app/package-lock.json` = 0; survey-web-desktop.md:131,134-135; survey-plans-decisions.md:56 (TS6 'no Playwright/browser dep' is an observation, not a prohibition).
- **[§4 sequencing — a minimal variant of step 2]** Steps 1 and 3 deliver almost all of the owner's 'quick' and 'focus on system tests'. Step 2 can be reduced to: (a) feed the selector's package list into `test` as a nextest filterset (~30 lines against the existing selector), (b) delete the ~770 lines that only prove the regex walkers agree with ci.yml plus coverage-policy.toml and the zero-user vocabulary, (c) the policy/guards merge. That keeps L1-L6 nominally in force and still removes ~1,500 LOC; the full job-table rewrite (-3,300) can follow once step 3 has proven the shape. Steps 4 (Swift half) and the weekly/hardware jobs can be dropped entirely.
  evidence: survey-infra.md:8 (770 of 1,654 lines are consistency proofs), :119 (replacement sizing), :124 (filterset lever).
- **[§2.7 lever 3 'auto-sync ~4 MB fixtures on first run']** This makes `obc test -p obc-route` do network I/O on first run — a behaviour change to the most basic local command. Alternative that keeps one feature shape without network: keep `obc_fixtures::read` panicking with the sync hint (the plan already says this in §2.2) and do not auto-sync; the fixture-dependent tests then fail loudly and locally-explicitly, which is the owner's fail-closed style.
  evidence: plan §2.2 ('obc_fixtures::read panics with the sync hint if absent') vs §2.7 lever 3 ('auto-sync ... on first run') — the two sentences prescribe different behaviours.
- **[§2.9 vectors 'one producer (obc-vectors regen) that also writes manifest.json']** Fine, but small and separable; it is not on the path to any of the six requirements. Land it last or leave it as a follow-up so step 5 does not grow.
  evidence: survey-critic.md verified_claims (manifest.json 1,632 lines hand-maintained; two comments reference it).
