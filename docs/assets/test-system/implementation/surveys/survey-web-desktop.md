# web-desktop — Web builder (builder/app vitest), WebAssembly bridges (obc-web-convert / obc-web-assemble / obc-skin-preview / obc-web-demo), desktop app (apps/obc-desktop), builder Python server + pytest, rain-radar-demo, and CI jobs wasm / wasm-bridges / web / desktop-frontend / desktop

## how_it_works
Web builder. Vitest runs under Node (builder/app/vite.config.ts:107-110, environment "node"); five component files opt into happy-dom per file and mount Svelte components with `mount()` from "svelte" (DownloadStep.svelte.test.ts:1-2, MapSend.svelte.test.ts:1-2). Nothing runs in a real browser. The `$host` alias picks one of three platform modules at build time (vite.config.ts:12-17, 48-52); wire tests import each host directly and record fetch/invoke calls (platform/dev.wire.test.ts:5-10, desktop.wire.test.ts:4-12, gating.test.ts:11-13).

The device link is faked at the byte-pipe seam, not the API seam. `DeviceLink { control: BytePipe, stream: BytePipe, vendorIn? }` (src/lib/usb/pipe.ts:12-31, 86, 124-155) has three implementations: WebUSB (webusb.ts), nusb-over-Tauri (desktop/usb.ts) and the loopback (loopback.ts). `loopbackLink()` (loopback.ts:258-300) builds four `Channel`s that re-slice every write to `packetSize` and park writers at a high-water mark (lines 67-160); `MockDevice` (lines 352-943) is a full protocol-v4 store: id assignment, (ObjectId,Revision) compare-and-swap, `busy`, `noSpace` with bytes required, paged LIST, bilateral cancel, ARM policy, and a `faults` log the flow tests assert empty on close (flows.test.ts:96-107). `loopbackDevice()` (lines 957-982) returns `{client: FlatStoreClient, device, link, close}` — the one-liner every flow test starts from. The three transport suites reuse the same device behind three different seams: client.test.ts drives FlatStoreClient directly; webusb.test.ts fakes `navigator.usb` (260-line prologue, lines 1-259) with a MockDevice behind it; desktop/usb.test.ts fakes the Tauri `invoke()` boundary (232-line prologue, lines 1-232) forwarding to a MockDevice. The flow tests (flows/rides/library/dashboard/manage) drive the shipping write.ts/rides.ts/library.ts code over that client and read the device's store back (`device.payloadOf`, `device.entries`). Route conversion inside those flows is the real wasm bridge, loaded from `src/lib/convert/pkg/obc_web_convert_bg.wasm` in a beforeAll that throws if `npm run build:wasm` was not run (flows.test.ts:52-58; same block copied in rides.test.ts:67-73, library.test.ts:55-61, convert/bridge.test.ts:73-82, assemble/bridge.test.ts:158-167).

The same loopback drives the real app in a browser through `dev-harness/main.ts` (claims `deviceHolder.open(openSimulatedSession)` before mount, line 23) — but only by hand; no job opens it.

Wasm bridges. `builder/build-wasm-bridges.sh` runs wasm-pack for three crates into `builder/app/src/lib/{convert,assemble,skin}/pkg`. CI's `wasm-bridges` job builds them, gates size with `firmware/tools/wasm_size_guard.py` (gzipped wasm+glue and raw wasm budgets, lines 114-118) and uploads the pkg dirs; `web` and `desktop-frontend` download them so vitest runs on the shipped bytes (ci.yml:942-962, 1024-1040). Byte-identity is asserted twice per bridge: natively (obc-web-convert convert.rs:500-509 vs specs/vectors; obc-web-assemble tests/determinism.rs:139 vs tests/fixture/expected written by the obcm-assemble CLI, provenance in tests/fixture.rs:1-40) and from Node on the wasm build (convert/bridge.test.ts:85-116, assemble/bridge.test.ts:170-215). The skin bridge is the exception: skin/preview.test.ts:9-16 vi.mock()s `./pkg/obc_skin_preview.js`, so its wasm build is exercised only by the size guard and svelte-check.

Desktop. apps/obc-desktop is a standalone Cargo root (Cargo.toml:8-17) whose `tauri::generate_context!` embeds `builder/app/dist/desktop`. CI builds and `cargo test --release`s it on three OSes (ci.yml:1060-1157) but never launches it; the 27 inline tests are filesystem/durability tests of rides.rs (682-1189) plus one canonicalise-policy test (usb/mod.rs) and two tokio `nusb` guards (usb/runtime_guard.rs), one of which needs hardware and self-skips. The Rust byte pipe over nusb lives in host/obc-usb (966 LOC, 11 tests) and is exercised on the TS side only through the fake `invoke()` backend.

Builder server. builder/server/server.py is a FastAPI maintainer host (endpoints lines 95-218); builder/tests drive `_catalog_url`/proxy validation and the schema-preview job directly, and shell out to `target/release/obc-pack` over `builder/tests/corpus/data/tiny.osm.pbf` to byte-compare the §8.6 profile table (test_routing_profiles.py:46-101). rain-radar-demo decodes specs/vectors/*.obcg with its own browser decoder (tests/obcg.test.ts:5-12).

Cross-language picture for the device fake (question 2). TypeScript: MockDevice, 982 LOC, hand-written protocol model, product-grade. Rust: the REAL engine — firmware/obc-link (no_std, alloc-free, transport-free; lib.rs:7 `#![no_std]`, engine.rs 1,841 LOC) bound to the real FlatStore over a deterministic sparse card (firmware/obc-storage/src/flat/sim.rs, 656 LOC, feature `std`) through `firmware/obc-link/tests/flat_harness/mod.rs` (588 LOC): `Device<D: BlockDevice>` with `control(&[u8]) -> Wire` and `stream(&[u8]) -> Wire` (lines 109-125) drives 1,414 + 452 LOC of engine/break-matrix tests. Swift: `TransferLink` protocol (OBCProtocolV4/TransferClient.swift:7-16: send/receive control and stream records, cancel, restore) implemented per test by scripted actors (`DisconnectingLink` TransferClientTests.swift:352, `PagedIdentityLink` :228); the separate OBCMock module (2,706 LOC) is domain-level with 'no wire protocol' by design (MockTransfer.swift header, MockTransport.swift header 'bypasses BLEChannel entirely'). `cargo tree -p obc-storage --features std --target wasm32-unknown-unknown` shows only heapless, embedded-sdmmc (default-features off), byteorder, obc-crc, obc-formats, obc-link — so the real engine + sim card is wasm-buildable today.

## strengths
- The loopback is protocol-faithful where fakes usually cheat: packet re-slicing on both channels and byte backpressure (loopback.ts:67-160), so reassembly and queue-without-retire bugs fail in CI; flows.test.ts:96-107 asserts the device's own fault log is empty after every happy path.
- 4,115 LOC of tests drive the shipping client/flow/session code end to end with no hardware and no phone, covering cancel-mid-send, unplug-mid-transfer, checksum refusal + retry on the same link, busy, and no-space (flows.test.ts:212-320).
- One three-language byte contract: specs/vectors/flat-store-v4 is pinned in TS (vectors.test.ts, 79 tests incl. manifest-coverage guard lines 560-586), Rust (obc-link/src/flat/vectors.rs) and Swift (FlatStoreVectorTests.swift).
- The wasm bridge tests run on the exact artifact CI ships (wasm-bridges → web artifact hand-off, ci.yml:812-829 / 952-962), and the assemble bridge is held to bytes the native CLI wrote (tests/fixture.rs provenance).
- Build-product guards assert on emitted Rollup chunks, not source greps: loopback.ts never ships (bundle.test.ts:352-370), USB stack stays code-split (:337-350), no absolute site URL survives a deploy build (:283-296).
- The suite is fast in aggregate: 33.7 s wall in CI for 972 tests; 62 of 65 files finish under 300 ms; `web` job is 70 s end to end when selected.
- A structurally unshippable real-browser harness already exists (builder/app/dev-harness, 675 LOC) and runs the whole app against the simulated device with paced transfers — the smoke target is built, only un-driven.
- obc-desktop's rides.rs tests exercise real crash points between write() and fsync() on the real filesystem (rides.rs:582-639), which is exactly what Node cannot prove (library.test.ts:10-17 says so).

## no_hil_story
Nothing in this area needs a device or a phone today, and it should stay that way. What cannot be exercised without hardware is precise and small: (1) nusb enumeration/open on a real bus (apps/obc-desktop/src/usb/runtime_guard.rs second test, host/obc-usb/src/lib.rs endpoint discovery), (2) WebUSB descriptor match and WinUSB/MS OS 2.0 binding in a real Chromium against a real board (webusb.test.ts header lines 17-19), (3) real SD write throughput. Those belong to the firmware/HIL story, not here.

Seams that exist: TypeScript `DeviceLink`/`BytePipe` (builder/app/src/lib/usb/pipe.ts:12-31, 86-155) with the loopback implementation (loopback.ts:258-300); the fake Tauri `invoke()` backend (desktop/usb.test.ts:1-232); the scripted `navigator.usb` (webusb.test.ts:1-259); the modelled OPFS (cells/store.test.ts:25-139); the Rust `Device<D: BlockDevice>::control/stream` harness over the real engine and sim card (firmware/obc-link/tests/flat_harness/mod.rs:109-125, obc-storage/src/flat/sim.rs SparseDisk/FaultOnce/When); the Swift `TransferLink` protocol (OBCProtocolV4/TransferClient.swift:7-16); the dev-harness session (dev-harness/simulated-device.svelte.ts openSimulatedSession, main.ts:23).

The gap is not hardware; it is the browser. OPFS sync access handles, module Workers running the assemble wasm, disk-backed Blob streaming, the permission prompt, and memory (#1503) are only ever modelled in Node.

Minimal seam that closes both the fake-divergence and the browser gap: (a) `apps/obc-virtual-device` — wasm-bindgen over `obc_link::flat::Engine` + `obc_storage::flat::FlatStore<SparseDisk>` exposing `control(bytes)`, `stream(bytes)`, `seed`, `entries`, `payloadOf`, `faultOnce`, `powerCut`; `cargo tree --target wasm32-unknown-unknown` shows the graph is pure Rust (heapless, embedded-sdmmc without defaults, byteorder). loopback.ts keeps only Channel/LoopbackPipe and calls into it. (b) One Playwright spec (`@playwright/test` + `playwright-core`, ~8 MB npm; use `channel: 'chrome'` on ubuntu-latest, which ships Google Chrome, so no 170 MB Chromium download; locally the user's Chrome) that opens the existing /dev-harness/ under `vite --mode web`, and asserts: connect chip says Connected, the route vector uploads and lists, the fixture cells assemble through the real Worker+OPFS to the SHA-256 of apps/obc-web-assemble/tests/fixture/expected/map.obcm, and `performance.measureUserAgentSpecificMemory()` (or the exported WebAssembly.Memory the #1503 experiment captured) stays under the estimator's number. Later HIL modularity: the same spec with `OBC_REAL_DEVICE=1` skips the harness entry and uses the real WebUSB path — the seam is the entry point, not the test.
