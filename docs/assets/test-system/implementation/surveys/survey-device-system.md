# device-system — Device application as a host-side system under test: obc-app (inline + tests/ + src/harness), obc-ports/obc-platform, obc-host-core (HostLoop, trace runner, DeviceCore conformance corpus), obc-sim (headless --png/--script driver, dirty_parity), ui-snapshots.sh + manifest, obc-replay, and the board crate obc-fw-nrf54l (RideExec)

## how_it_works
The seam is real and clean. The whole product behaviour lives in `obc-app::App`, and every host drives it with exactly one call per frame: `App::run_pass(PassInputs) -> PassPlan` (firmware/obc-app/src/device_core/pass.rs:348). `PassInputs` (pass.rs:162-185) is pull-only: two clocks, the recognised gestures, `obc_ports::Sensors` (location/fuel/HR/… trait objects), an optional `RouteReader`, an optional weather snapshot, a `PlatformSupport` capability record, plus the executor's inbox: `OutcomeSlots` (one typed answer per domain), `ExternalFacts`, and keyed `DerivedInputs`. The pass runs 14 fixed stages (pass.rs:92-140) and returns a `PassPlan` (pass.rs:201-215): which planes to repaint (`Dirty`), the next wake, the sources it needs open, and `EffectSlots` — one bounded typed effect per domain (catalog, retention, recorder, navigator, settings, weather, dfu, bond, storage_info). Rendering is a separate call over any `embedded_graphics::DrawTarget` (`App::render_frame`, app.rs:3173). So a host-side virtual device is: scripted ports in, run_pass, serve effects against in-memory stores, put outcomes back, render into a buffer, assert. Every piece of that already exists somewhere, just not in one place.

Executors. The thing between two passes — 'serve the effects and deposit outcomes' — is implemented six times: (1) production `HostLoop` in host/obc-host-core/src/dispatch.rs:217-834 (used by the sim GUI gui.rs:553/736/809, the sim headless settle main.rs:800-866, present.rs demos, the web demo) with the `HostPlatform` trait (dispatch.rs:143-191) for what only a physical host can do and `Mem*` repositories (stores.rs); (2) production `RideExec` + `run_app` on the board (firmware/obc-fw-nrf54l/src/ride.rs:641-740 and the loop after ~800), hand-written against the same slots, with phase order dictated by hardware (guard split, bulge-first, arena claims) — zero host tests; (3) `CoreHarness` inside the conformance test (host/obc-host-core/tests/device_core_conformance.rs:186-~720) — a third full executor written so the corpus is 'executor-independent'; (4) `Planner` in obc-app's support.rs:447-708 (navigation only, settles up to 8 passes); (5) `Sweeper` in app.rs tests:6710-6800 (catalog/retention only); (6) `drive_replay` in apps/obc-sim/tests/dirty_parity.rs:1110-1170. Three of the six are test-only re-implementations of what HostLoop already does.

Scenario input DSLs. There are five ways to say 'tap Select, send a fix': obc-sim's character script `d u p b h B H M w f T C` fed through `App::handle_input` (main.rs:930-1010, 917); dirty_parity's `Step` builder with `.keys/.fix/.hr/.power/.cadence/.feed/.fact/.weather/.probe/.expect` (dirty_parity.rs:205-300); the conformance corpus's 70-variant `Action` enum applied by `CorpusState::apply_input` (corpus:206-270); support.rs's `keys/tap/step/down/up` + `Frames::frame(app, ms, evs, fix, battery)` (support.rs:130-156, 382-410); and the VCOM wire lines `K s d\nK s u`, `F lat lon`, `A m`, `Z mpp` whose codec is host-tested in obc-platform/src/debug_link.rs (997 LOC, 26 tests) and spoken by tools/s6b_board_cutover_soak.py.

Observed outputs. Assertions are on: (a) the screen stack (`app.top_screen()`, `Screen::…` variants) — everywhere; (b) typed effects and outcomes taken from `plan.effects.<domain>` (support.rs:465-490, screens.rs:30-40); (c) rider-visible normalized state — the 25-field `VisibleState` snapshot the conformance runner records after every input/pass/delivery and compares across the two answer cadences (corpus:297-325, conformance.rs:724); (d) pixels — obc-app's `Buf` counts colours (support.rs:31-70; i18n.rs renders 11 frames), dirty_parity compares two whole framebuffers per pass, and the sweep hashes 317 PNGs; (e) private state — app.rs tests read `app.ui.*` 131 times and `app.activity.*` 20 times, the harness reads Navigator readouts, and 30 `#[cfg(test)]`-only accessor fns exist on the machines (grep count; e.g. pass.rs:1027-1062 test_mount_store/test_start_ride/test_end_ride/pass_trace).

Where the 989 inline tests sit and why. 21,701 LOC of `#[cfg(test)] mod` blocks in obc-app/src (my brace-matched count; the 43,761 firmware figure given used a different method — mine is 31,748 for all of firmware/, of which obc-app is 68%) plus 3,529 LOC of in-crate harness = 25,230 LOC of test code inside the lib target, against 41,771 LOC of production; with tests/ (6,122) the crate is 43% test. The breakdown matters: ~16.4k LOC / 700 tests are genuine unit tests of pure machines (recorder, settings, stat_fields, retention, weather, render_key, card_scheduler, input, navigator, slots — 0 `App::new_idle` in those files) and of screens through a hand-assembled `Ctx` (screen::test_ctx, screen/mod.rs:306, 33 files). Those belong inline. The other ~8.8k LOC / 289 tests (app.rs 4,146/140, pass.rs 1,146/34, harness 3,529/115) are staged-App scenarios — they build an App, press buttons, tick, run passes and assert on screens/effects. They are system tests placed inline because staging (an on-route riding app with a known `progress_m`) and reading (`app.ui.now_ms`, idle timers) need `pub(crate)`; harness/mod.rs:1-13 and lib.rs:14-27 say so explicitly and pay for it with `#![cfg_attr(not(test), no_std)]`, `extern crate self as obc_app`, and compiling support.rs twice via a `#[path]` include.

Snapshot sweep mechanics. firmware/ui-snapshots.sh syncs the grimsel/monaco fixtures (tools/fixtures.py sync sim, line 46), stages temp route/track dirs, then launches obc-sim 233 times with `--boot --script … --expect-screen NAME --png` (e.g. ui-snapshots.sh:195-240); each launch parses the map, replays the character script through handle_input, settles through HostLoop, renders once. ui_snapshot_manifest.py check compares sha256 rows and also fails on two frames with identical pixels unless declared IDENTICAL_BY_DESIGN (manifest.py:1-40). In CI it is an unconditional step of the `test` job (ci.yml:321-325), which itself runs `cargo nextest run --workspace --all-features` over all 191 test binaries (ci.yml:284) whenever the selection job includes `test` — so for Rust the registry's 'affected' selection is job-granular, not suite-granular.

Board side. The board crate has no test target and its registry suite is a release build (suites.toml:93-102). What is unique to it: the executor phase order and `owed()` wake folding (ride.rs:689-735), GPS power policy (ride.rs:741), watchdog feed gating (ride.rs:60-76), arena claim/release, the boot-time ride recovery (ride.rs:875-890 → flat_ride.rs:249-272; footer decode into `RideContinuation` at flat_ride.rs:805-838), and the three cfg-gated run_pass call sites (ride.rs:2383/2407/2431). These are exactly the A–K soak scenarios of tools/s6b_board_cutover_soak.py:580-941, which is the only evidence and is scheduled for deletion.

## strengths
- The architecture seam is genuinely testable without hardware: run_pass(PassInputs)->PassPlan with typed per-domain effect/outcome slots (pass.rs:162-215, slots.rs) is driven identically by the board, the simulator, the web demo and every test; no callback can reach into the core mid-pass (pass.rs:2039 test pins it).
- The DeviceCore conformance corpus is the best system-test asset in the repo: 24 scenarios × 61 requirement rows × 2 answer cadences compared on rider-visible state, with coverage gates (every requirement claimed, every feeder exercised) — and it found two production defects (device_core_conformance.rs:22-33).
- dirty_parity is an oracle without goldens: reference-renders-every-pass vs candidate-renders-on-demand, byte-compared per pass, with a repaint-count ceiling (dirty_parity.rs:1-22, 1169-1300). Nothing to 'update' when pixels legitimately change.
- Domain machines (recorder, settings, retention, weather, stat_fields, card_scheduler) are pure and unit-tested without an App; those ~16k inline LOC are correctly placed.
- The sweep's --expect-screen rule (ui-snapshots.sh:19-26) turns a silently-wrong recipe into a failure, and the manifest's identical-pixels check catches mislabelled frames (ui_snapshot_manifest.py:12-19).
- HostLoop is a shared production executor with a defaulted HostPlatform trait (dispatch.rs:143-191) and in-memory Mem* stores (stores.rs) — everything a host-side virtual device needs is already a library.
- The VCOM wire codec (obc-platform/src/debug_link.rs, 26 tests) is host-tested and shared verbatim with the board, so a later HIL transport can reuse a host-side script format instead of inventing one.
- Test names read as behaviour sentences and module docs state intent; the audit memory's finding (protective, few tautologies) still holds in what I read.

## problems
- [high] The effect-executor protocol is implemented six times; three of them are test-only re-implementations of HostLoop (CoreHarness ~530 LOC, Planner 260 LOC, Sweeper ~90 LOC) and one production copy (board RideExec/run_app) has no host test at all.
  evidence: host/obc-host-core/src/dispatch.rs:217-834 (HostLoop); firmware/obc-fw-nrf54l/src/ride.rs:641-740 (RideExec) + run_pass sites ride.rs:2383/2407/2431; host/obc-host-core/tests/device_core_conformance.rs:186-720 (CoreHarness); firmware/obc-app/src/harness/support.rs:447-708 (Planner); firmware/obc-app/src/app.rs:6710-6800 (Sweeper); apps/obc-sim/tests/dirty_parity.rs:1110-1170 (drive_replay)

  evidence: harness/mod.rs:1-13 and lib.rs:14-27 explain the relocation; app.rs test module reads app.ui.* 131× and app.activity.* 20×; 30 #[cfg(test)]-only accessor fns (e.g. pass.rs:1027-1062); support.rs compiled twice via tests/common/mod.rs:9 #[path] include; `extern crate self as obc_app` lib.rs:26
