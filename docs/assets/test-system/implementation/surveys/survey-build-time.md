## strengths
- The opt-level=2 package overrides in Cargo.toml are the right kind of lever and are documented with measured numbers (obc-storage 137 s -> 5.4 s); nothing in this survey suggests extending them.
- CI cache design is correct: one shared-key `host-tests` cache written only on develop pushes (ci.yml:252-262), restore-only in the weather legs (408-412); restore costs 13 s and the whole compile+run of 159 binaries is 93 s.
- nextest in CI is the right runner for a 159-binary workspace (one pool instead of serial binaries); the ci.yml:234-237 comment records the 470 s -> 40 s measurement.
- No-op and single-test-file rebuilds are fast (0.37 s / 0.62-0.85 s): cargo fingerprinting works, incremental works, dependencies are warm.
- obc-app's 1,149 tests run in 4.2 s wall; only two breadcrumb tests exceed 1 s. Test execution is not the problem anywhere in the app crate.
- The per-package `obc test -p obc-app` compiles the device feature shape (obc-reader [], obc-formats [default]) — the local focused loop tests what the device links.

## no_hil_story
Build and execution time itself needs no hardware. The device-image build is already board-free: CI `embedded` builds obc-app and obc-link for thumbv8m.main-none-eabihf (ci.yml:686-694), the board crate legs clippy/build it (ci.yml:462-466), and the FLPR blob only needs a RISC-V gcc (tools/obc-dev.sh:61-84 ensure_riscv). Nothing in the host test loop touches a phone or board. The one seam this area exposes: the firmware crates' host test build should compile the device feature shape (obc-reader [], obc-formats [default], obc-route []) — `cargo test -p obc-app` does, `--workspace --all-features` does not — so a host-side system test of the app is only a faithful stand-in for the device when the per-package default shape is the one run. Keeping that shape as the single test shape is the minimal seam; no fakes or replays are needed for timing work.
