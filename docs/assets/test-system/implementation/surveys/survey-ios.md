## how_it_works
Layering (Package.swift:5-22, companion-ios/CLAUDE.md 'Architecture'): OBCDomain -> OBCProtocolV4 / OBCWeatherWire -> OBCWeather -> OBCTransport -> OBCMock; OBCUI depends on OBCDomain+OBCTransport+OBCWeather. Every view model takes capability-sized protocols (DeviceLink, DeviceObjects, DeviceRetention, DeviceUpdates, ... in Sources/OBCTransport/DeviceTransport.swift:27-233) and the aggregate DeviceTransport (:206-215) has two conformers: BLETransport (real, 2,603 LOC, CoreBluetooth created inside init at BLETransport.swift:188-194, 22 CBPeripheral/CBCentralManager references, no injectable central/peripheral seam) and MockTransport (Debug-only, MockTransport.swift). The composition root picks one from launch args (OBCCompanionApp.swift:21-34,128; MockLaunchOptions.swift:12-30 documents 16 launch flags that XCUITests and the screenshot script drive).

Host tests ('swift test', macOS, no simulator) drive the code three ways: (1) codec/contract pins against specs/vectors/* read via #filePath (FlatStoreVectorTests.swift:84-90 manifest-driven; DeviceCommandTests.swift:8-15 and five sibling files each re-derive the vectors path); (2) view-model flow tests that build MockControl(scenario:), zero its latency, load a fixture set, seed an InMemoryLibraryStore (Sources/OBCTransport/Library/LibraryStore.swift:94), start MainScreenModel, and poll with the throwing waitFor(...) helper (Tests/OBCUITests/Support/WaitFor.swift:16-31, plus neverHolds :35-42 for negative windows) - e.g. TripUploadModelTests.swift:19-29; (3) hand-written stub transports/links per file where the mock's knobs do not reach (10 stubs in OBCUITests, 4 TransferLink actors in TransferClientTests, ScriptedLink in WeatherJobEngineTests:31). Assertions are on model state (loadState, rows, banners), on MockControl's recorded evidence (setClock samples, forgetBond count, routeRetention writes: MockControl.swift:99-139), and on bytes for codecs.

The protocol-v4 transfer path is factored so it is host-testable without radio: TransferClient (actor, OBCProtocolV4/TransferClient.swift:37-49) depends only on `TransferLink` (:7-16: sendControlRecord/receiveControlRecord/sendStreamRecord/receiveStreamRecord/cancel*/restore); BLETransport conforms at BLETransport.swift:2023; BLEChannel (BLE/BLEChannel.swift) frames records over the `ByteChannel` byte pipe (BLE/ByteChannel.swift:10-21) whose real conformer is L2CAPByteChannel. Nothing on the Swift side speaks to firmware code: every device response in tests is written by hand in Swift.

XCUITests run the real app in the simulator against MockTransport via launch args; each file has its own launch(...) helper. CI (ci.yml:851-927): ios-unit = swift test with --xunit-output (Swift Testing results uploaded, docs/testing.md:181-197); ios-app = xcodegen + Debug build + marker grep + screenshot drift check (which runs only WebsiteScreenshotTests) + Release build + marker-absent grep. Selection: suite_registry.py derives job routes from workflow command patterns (suite_workflow_jobs, tools/suite_registry.py:887-904); the swift suite's extra_triggers (suites.toml:634) and ci.ios-app-build's (suites.toml:918-924) both include Packages/OBCKit/Sources/**, so any OBCKit source change runs both jobs (~2 min + 13-18 min).

## strengths
- The transport seam is real and already the right shape for a phone-less system test: TransferLink (OBCProtocolV4/TransferClient.swift:7-16) is eight async record-level calls with no CoreBluetooth type, and TransferClient is a plain actor; BLETransport conforms to it at BLETransport.swift:2023. A fake peripheral can plug in there without touching production code.
- CoreBluetooth is confined and the confinement is test-enforced (CoreBluetoothSeamTests.swift:12-19 scans Sources for the import outside OBCTransport/BLE/; OBCCompanion/ is checked at :22-31).
- Shared vectors are the contract and Swift consumes them: FlatStoreVectorTests.swift is manifest-driven over 68 flat-store-v4 vectors produced by hand from the spec in Rust (firmware/obc-link/src/flat/vectors.rs:1-16); command/status/config/OBCU/ride/trip/OBCW/OBCG bytes are pinned on both sides (firmware/obc-ble/tests/vectors.rs:1-4 says so explicitly).
- The Swift Testing half is fast and parallel: 567 cases in 12.35 s wall (ios-unit-swift-testing.xml); the whole ios-unit step is 1.8-2.5 min, dominated by compiling 36k LOC of Swift 6 sources, not by tests.
- The mock is a good scenario driver, not just a stub: one-shot faults, pairing failure phase, radio state, drop-at-fraction with realistic restart semantics (MockTransfer.swift:8-19), old-firmware capability knob, recorded evidence counters (MockControl.swift:99-139). 16 named scenarios (Scenario.swift:26-47) map one-to-one onto design-doc screens.
- The #1236 waitFor consolidation landed: one throwing MainActor helper plus neverHolds (Tests/OBCUITests/Support/WaitFor.swift), so a timeout fails once and stops.
- The Debug/Release mock-marker grep (ci.yml:905-926) is a cheap, non-vacuous proof that dev-panel code never ships.
- Swift Testing is the standard for new suites (memory ios-hardening-epic-354; CLAUDE.md conventions) and already holds 567 of 916 test functions.

What exists as seams: (1) TransferLink (OBCProtocolV4/TransferClient.swift:7-16) - eight record-level async calls; everything above it (TransferClient put/get/list/status/remove, STATUS reconcile after TransferLinkLost, request-id lifecycle) is pure Swift and already tested against hand-scripted links. (3) On the Rust side the device engine is host-runnable and transport-free: firmware/obc-link (Cargo.toml description 'no_std, allocation-free, transport-free'; flat::engine, flat::wire, flat::store seam) bound to obc_storage::flat::FlatStore over a sim BlockDevice, with fault injection (obc_storage::flat::sim::{FaultOnce, MediaOp}) - see tests/flat_harness/mod.rs:109-225 (Device::control(&[u8]) -> Wire, stream(&[u8]) -> Wire, link_lost(), watch_stall(), seed(kind, bytes, name)). Minimal seam to add (no production Swift changes): a dev-only Rust binary in host/ (name it after what it is, e.g. obc-flat-device) that boots a flat_harness-style Device on a sim card and speaks two length-prefixed lanes over stdio or a TCP port - lane 0 control records, lane 1 stream records - plus a side channel for faults (drop link now, media fault once, seed object). Swift side: `ProcessTransferLink: TransferLink` (~100 LOC) in a test-support target that spawns the binary via Foundation.Process; the GATT control plane (config/command/status codecs) stays a small Swift fake because it is codec-pinned by shared vectors and has no engine on the device beyond the command handlers in obc-app. Then TransferClientTests' four scripted links become scenarios on the real engine, a new 'device conformance' suite runs put/get/list/status/remove/cancel/drop-and-reconcile against firmware truth, and the TS FlatStoreClient can point at the same process, retiring loopback.ts. Later HIL tiers slot in by conforming a real BLE link (or a DK-over-USB pipe from host/obc-usb) to the identical TransferLink and re-running the conformance suite unchanged.
