# infra — Test infrastructure itself: registry (testing/suites.toml, coverage-policy.toml), selector (tools/suite_registry.py), local commands (tools/justfile, obc-dev.sh), CI workflow (.github/workflows/ci.yml, test-exception-health.yml), aggregate gate (tools/ci_aggregate.py), guards (tools/check_*.py, firmware/tools/*), tooling tests (tools/tests), and the policy docs (docs/testing.md, CONTRIBUTING.md, AGENTS.md).

## how_it_works
Selection chain (one implementation, three consumers). `suite_registry.py select` (1514-1524) loads both TOML registries, discovers execution units four ways — `cargo metadata --no-deps` over the root workspace plus three standalone manifests (225-260), file globs under 7 hard-coded non-Rust roots (263-283), a regex over OBCKit's Package.swift (286-298), and a hand-written line-by-line scanner of ci.yml `run:` steps (308-374) — then `validate()` (494-610) requires exactly one owner suite per discovered unit and rejects derived fields, bad cadences, live-looking commands, unregistered sleeps, and dead entries. `build_cargo_graph` (633-669) derives reverse dependency edges from cargo metadata. `suite_workflow_jobs` (887-904) maps each suite to CI jobs by parsing every workflow step's `cargo`/`wasm-pack`/`trunk` invocation into package sets (756-884). `select_suites` (981-1109) walks `git diff --name-only` and adds a reason per suite for: policy paths (TEST_POLICY_PATTERNS 63-78 → every workflow-owned suite), foundational Rust files (1015-1034 → hard-coded list of 8 ci.* ids), changed Cargo packages and their reverse closure (1036-1050), fixtures/ (1052-1056), `extra_triggers` globs and owned test paths (1058-1069); an unowned production-looking path is a hard error (1073-1076). `pull_request = "always"` suites ride along on jobs already started (1083-1094). `required_jobs` (914-925) closes over the `needs` graph. CI: the `selection` job (ci.yml:57-93) publishes `plan` and `jobs`; every gated job has `if: contains(fromJSON(needs.selection.outputs.jobs), '<own name>')` (e.g. 178, 207, 243); the `ci` job (1159-1171) hands the plan and `toJSON(needs)` to ci_aggregate.py, which classifies each of the 69 suites as pass / fail / not selected / selected-but-not-run / blocked (71-143) and fails on any of the last three. `validate-filters` (1311-1369) proves the regex-parsed workflow and the plan agree: every routed job exists and has a runner, every job hosts a suite and is in the gate's needs, every gated job gates on its own literal name, and 16 AUDITED_PATHS (1287-1304) select without error. Locally, `obc test affected` = `suite_registry.py run --affected` (justfile:592) which prints the plan and executes each selected suite's `command` string serially via `bash -c` (1210-1220), skipping platform-restricted ones; `obc test unit|component|contract|fixtures|e2e` selects by level (1153-1185); `obc check <gates>` (justfile:662-755) re-implements the CI step commands in bash and asks the registry which suites each gate claims (`gates`, 1544-1583) via the `obc check X` strings in ci.* suite commands (1224-1259). Assertions in the tooling tests are on: synthetic-repo rejection messages (test_suite_registry.py:106-146), selection reasons and job sets for a 4-crate synthetic graph (252-450), regex workflow parsing (172-250), and a hand-maintained table of expected job sets per change class against the real registry (762-830). Measured behaviour on develop (run 34727869462): selection 13 s, guards 6-13 s each, test 233 s, clippy 50 s, wasm-bridges 66 s, 10 jobs skipped, ci 8 s. Simulated selections (select_suites over the real registry): firmware/obc-app/src/lib.rs → 21 suites / 16 jobs (test, clippy, device, embedded, wasm, wasm-bridges + 9 unconditional); firmware/obc-formats/src/lib.rs → 41 suites / 19 jobs incl. test-weather (4 legs) and desktop (3 OS); CLAUDE.md → 32 suites / 25 jobs incl. ios-app and desktop; README.md or docs/content/*.md → 9-10 suites, only the unconditional jobs (+docs).

## strengths
- Single selector, fail-closed: an unowned production path (suite_registry.py:1073-1076) or a selected suite with no CI route (1096-1101) fails CI rather than silently running nothing; `--no-tests fail` on every nextest leg (ci.yml:238-240).
- Derived, not copied: Cargo graph and targets come from `cargo metadata` (225-260, 633-669); DERIVED_FIELDS (40-47) forbids counts/durations in TOML. This is the right instinct and survives any redesign.
- The job-level gating actually works: a docs-only change starts 10 jobs of 26; the 4-leg weather matrix and the 3-OS desktop matrix stay off unless their inputs change (verified by simulation and by ShippedRoutingTests 762-830).
- Every `obc test` form prints the plan with one reason per suite before running (run_plan 1195-1201); `--dry-run` is cheap (0.6 s) and honest about platform skips (1212-1214).
- One aggregate `ci` job is the only required status check, and a failed `selection` job fails it instead of passing vacuously (ci.yml:88-90, 1155-1158).
- The nextest switch is well justified and measured (ci.yml:234-237: ~470 s → 40 s for the same tests).
- Guards state their own limits honestly ('This is a blocklist of names, and that is all it is', check_render_keys.py, check_catalog_ownership.py, check_retention_ownership.py) and name the real test that covers the semantic case.
- Registry validation is fast (check 0.6 s, validate-filters 0.7 s measured) and offline; the only online piece is the separate weekly issue check.

## problems
- [high] Suite-level precision is thrown away at the job boundary. Any Rust source change selects the `test` job, which is literally `cargo nextest run --workspace --all-features` (ci.yml:284) plus doctests, obc-formats default-features, two python suites, check_dependencies, obc-bench release, a full ui-snapshots sweep, an obc-pack release build and the builder pytest (ci.yml:287-339): 233 s on develop for a one-crate change. ~770 lines of suite_registry.py compute which of 41 rust.* suites are affected, but CI never runs fewer than all of them.
  evidence: Simulated: firmware/obc-app/src/lib.rs → 21 suites but jobs = test (whole workspace). ci.yml:274-284; ci.yml:365-370 comment explains the matrix trick that keeps `test` as every package's route. Run 34727869462: test 233 s.

## no_hil_story
Within this area the HIL question is about routing, not devices. The registry already permits a `hardware` level with `pull_request = "never"` and `scheduled = "manual"` (suite_registry.py:28, 537-538) but zero suites use it; no workflow other than ci.yml is scanned (311), so a future HIL workflow would be invisible to the selector by design. The HIL tools that exist — tools/s6b_board_cutover_soak.py (999 LOC, VCOM-driven soak) and tools/bench_ingest.py (534 LOC, serial ingest) — sit in tools/ with parser-only unit tests (test_s6b_board_cutover_soak.py 234, test_bench_ingest.py 545) that run on every PR under python.repository-tools; the device-side halves are unreachable without a board. The board crate itself (obc-fw-nrf54l) is build-only in CI (ci.yml:17 'There is no board in CI') and its composition contracts are pinned by text-grep tests (firmware/tools/tests/test_fs7_board_composition.py, test_weather_ownership.py) because 'the nRF crate is Thumb-only, so … a host unit test cannot execute' them (test_fs7_board_composition.py:3-4). The seam that would let host-side system tests replace those greps is the host-side executor already named by the guards: host/obc-host-core/tests/device_core_conformance.rs and its device_core_corpus (check_catalog_ownership.py, check_retention_ownership.py docstrings) — the board composition should be exercised through that same conformance harness with a board-shaped executor rather than pinned by substring assertions. For the framework: a modular design needs only (a) a `hardware` job family that is never selected on PRs and is invoked by workflow_dispatch/schedule, (b) the same runner script (`tools/ci/<job>.sh`) callable locally with a board attached, and (c) no registry parsing of workflows — so adding HIL later is one job file, not a selector change.
